Method

How I test, count and correct.

Every lab on this site follows the same rules. This page is the short version, so you can judge a result before you trust it or quote it.

Last reviewed 15 November 2026.

The order is the method

  1. Write the case. A made-up company, the bad outcome I am looking for, and the controls that might stop it.
  2. Write my guess. For each case: does the bad outcome happen with the control on, and with it off?
  3. Lock the guess. I hash the guess file and commit it to the public repository before any code exists. After that I do not edit it.
  4. Only then write the code. A small model of the control on made-up data, with my assumptions written in comments.
  5. Run it, and run it again elsewhere. The results must come out the same on a second machine.
  6. Keep the wrong guesses. If my code was wrong, I fix the code and say so. If my guess was wrong, the guess stays on the page.

A locked guess does not prove I did not cheat. It makes cheating visible to anyone who checks the commit history.

What the numbers count

The labs use a few words for things that are easy to mix up. Here is what each one means.

  • Case: one situation with a bad outcome and the controls that could stop it. “130 cases” in the conditional access lab means 130 of these.
  • Run or round: one batch of cases, with its own locked guesses. The labs grew in runs, so early pages may quote a smaller number with words like “at launch”.
  • Scripted check: one automated request against a real piece of software, used in the MCP lab. 210 scripted checks over three rounds.
  • Case card: how checks are written up for reading. One card can cover a few closely related checks, so there are fewer cards (161) than checks (210).
  • Use case: a situation written down before testing, in a catalogue. Not every use case became a case.
  • Unit test: a test inside the code itself that protects it when I change it. These are not results.

All of these numbers live in one file, and an automatic check fails if a page quotes a number that does not match it.

What kind of evidence it is

Not every result is the same kind of evidence. Each result is one of these:

  • Model on made-up data. A script reproduces the logic of a control. No vendor product was involved. Most cases in the conditional access, machine identity and AI governance labs.
  • Hand-run against a real product. Real software, made-up data. The MCP lab used the official MCP Inspector and a real AI coding client against my own gateway.
  • Prediction locked, not yet run. The guess is committed, the test is not done. Example: run 4 of the conditional access lab.
  • Drawn from practice, anonymised. The case studies. Built from experience, with no employer or client data.
  • Opinion. My judgement, in articles and conclusions. I try to say when I am giving one.

How I correct mistakes

Wrong guesses are published next to the right ones, case by case. When a published number turns out to be wrong, I correct the page, say what changed, and publish an errata note: see the AI governance lab errata. If you find an error, tell me.

What the labs cannot show

  • How a vendor product behaves. The models copy rule logic, not products.
  • Anything about a real company. All data is made up.
  • Speed, cost, scale or legal compliance.
  • That my assumptions are right. Several results depend on choices written in the code; change one and a result can change.
