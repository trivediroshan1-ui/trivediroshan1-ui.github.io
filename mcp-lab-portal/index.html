MCP approval lab · 3 to 17 October 2026

Can a person stay in control of an AI agent?

I built a small approval gateway for MCP tool calls, then spent three rounds trying to break it. Here is what held, what did not, and what to ask before you trust an approval step in your own company.

Every tool call an agent makes walks this path. The lab tests each stop.

The short version

An agent asks. A person decides. Does that hold up?

More and more agents call real tools: they search documents, change records, deploy to production. The usual safety answer is that a person approves the risky ones. I wanted to know how much that answer is worth, so I tested one.

What held

  • A request changed after approval was refused: a new resource, an extra argument, a look-alike letter.
  • An approval ran once. Reuse and two runs at the same moment were blocked.
  • Expired approvals were refused, including in a real 11-minute wait.
  • An edited audit event was caught, and the log can be checked from outside.

What broke

  • An approval survived a loosened tool definition. Fixed.
  • A hidden character made the review screen show different text from the stored one. Fixed.
  • A request flipped to approved in the database ran with no human decision. Fixed.
  • A made-up reviewer name was accepted. Narrowed, not solved.

What I would ask for

  • Does the approval cover the exact request, the tool definition and the rules version?
  • Does the reviewer have a real identity, or just a typed name?
  • What reaches the tool at the end: the permit, the approver, anything?
  • Can the record be checked without trusting whoever wrote it?

The honest bottom line. None of this makes an agent safe. It shows which parts of an approval step you can test, how to test them, and where the weak spots were in mine. Everything ran on made-up tools and made-up data, on my own machines. It is not a certification.

Round three

The permit, the receipt, and who holds what

After a person says yes, three different parties hold three different pieces of the story. The agent gets proof that something ran. It does not get who allowed it. The tool at the end does not get the permit at all.

The agent gets back

16 fields on the execute reply.

executionIdrequestHashresultDigestidempotencyKeyoutcomeapprovalIdstateriskLeveland 8 moreapproverpolicy versionsignature

It can show that something ran. It cannot show who allowed it or under which rules.

The downstream tool gets

Exactly five fields.

toolIdactionresourceargumentsidempotencyKeyapproval idrequest hashapprover

The key is the gateway’s own dispatch key, not the one the agent sent. The tool cannot check that a person approved anything.

The audit log keeps

The only complete record.

approverrolepolicy versionrequest hashresult digest

Hash-chained, signed only if a key is set. In the demo, anyone who can reach the REST port can read it.

Why this matters. If an auditor asks “who approved this and under which rules?”, the answer lives on the gateway side only. A receipt format that travels with the call would have to carry the approver, the policy version and a signature. Mine does not. Round three measured exactly that, and it is on the list of limits.

What this does not show

It is one gateway

The results describe what this gateway did on these cases, once each, on my own machines. They say nothing about any product you may be buying.

The tools are made up

No real system, secret, customer or employer is involved. Real tools bring real delays, real errors and real people.

I wrote the tests

Nobody independent has reviewed this yet. I recorded my predictions first and kept the twelve I got wrong in the open, but a different person would think of different cases.

It is not a certification

A case that passed shows that case passed. It does not prove the gateway secure, and the report says so more than once.

Found a mistake or a case I missed? Tell me. Open an issue on the GitHub repository, or write through the contact details on the about page. I would rather correct it in the open.
