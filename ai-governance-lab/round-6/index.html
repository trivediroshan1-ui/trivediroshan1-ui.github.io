AI governance lab

Round 6 of the AI governance lab

An agent that only sends a request, while a gateway outside it decides and acts.

Last reviewed 14 November 2026

All rounds · Lab overview · Case explorer

Zoom in: agents that send instructions to an API (round six)

This zooms into steps 5 to 7 of the lifecycle above. An agent does not have to act on identities by itself. A safer pattern is that it only sends a request, and something else decides and acts. The request has a fixed shape, for example “disable this account”. A gateway outside the agent checks who the agent is, whether the action is on the list, whether a person must approve it and how many requests the agent has sent this hour. If everything passes, the gateway signs a decision. A separate program, the executor, checks the signature, borrows a short-lived credential from a vault, calls the identity API and gives the credential back.

The agent never holds the credential. That is the main design choice. Giving an agent “read access to the vault” so it can paste a password into an API call is the same mistake as giving an AI tool “read access on your domain”: it works, until something goes wrong.

I wrote the expected result for 18 new cases (T1 to T18) and saved them before writing any code, on 25 Oct 2026 at 00:28 IST. They cover a joiner, a leaver with approval, a prompt-injected delete, approvals by the wrong people, a request with a made-up address in it, an agent reaching for the vault, the kill switch with a credential already lent out, a repeated request, personal data in the reason text, 25 requests in an hour, a forged decision, a lease used after it ended, a static password that is rotated on check-in, and two cases about the limits of the whole idea.

All 18 came out as I guessed. As a check on the tests themselves, I switched off 12 controls one at a time in a copy of the code. At first, 12 of 12 stopped passing. Under the stricter rule I applied on 25 Oct 2026, 11 of 12 count as noticing, because the T5 case crashed with its control off instead of giving a different result.

Re-counted 25 Oct 2026. Round six control-off checks are now 11 of 12 under the strict rule (published: 12 of 12). T5 crashed instead of showing the bad approval go through. What changed and why. The book and addendum PDFs still show the older number: errata, page by page.

What this does not show

  • The vault and the identity API are small models I wrote for the lab. They are not HashiCorp Vault, Delinea Secret Server or any SCIM product, and a real tenant could behave differently.
  • The AI model behind an agent is not tested. Each case assumes the agent was fooled or wrong and tests the wall around it.
  • I wrote the guesses and the code, so “as expected” shows the rules do what I intended, not that I thought of every attack.
  • T15 is a limit: a wrong but allowed request (the wrong person with the same name) passes every check. T18 is an anti-pattern shown by construction, not a finding.
  • Not tested in this round: real SCIM calls, real approvals by people, and real mutual TLS between gateway and executor. Public-key signing, chains of agents handing work on, and a compromised gateway or executor are modelled in round eleven.

Questions I would ask a vendor who sells this

  • Does the agent ever hold the credential, even for a moment?
  • Can it ask for anything that is not on a fixed list, and can it name the address the call goes to?
  • Who approves a disable or a delete, and can that person be the one who set the agent up?
  • When you switch the agent off, what happens to a credential it already triggered?
  • Does the log keep names, free text or secrets?
