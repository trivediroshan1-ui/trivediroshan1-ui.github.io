Round 8 of the AI governance lab

What happens when an agent finds a way round the gateway, and how the response plays out.

Last reviewed 14 November 2026

All rounds · Lab overview · Case explorer

When an agent goes around the gateway (round eight)

The pattern above works only if the agent cannot get round it. So I asked the awkward question: what if it does? An agent might find a token in a config file, or hold a second tool with its own credential. This round tests three layers. First, make it hard: a credential works only from the caller it was lent to, and the agent’s runtime has no route to the identity system. Second, notice: every change in the identity system’s own log must match a decision the gateway signed, and a change with no decision is a bypass. Third, answer: switch the agent off, revoke what it could use, keep the evidence, and let a person decide what to undo.

The animation below is the first hour after a bypass alert. It is a design, tested here on small models, and it names who does each step.

  • Identity API and directory
  • Gateway, executor, policy
  • Security operations and audit
  • Sponsor and business unit
  • HR and legal
  • AI agent

  1. A change with no decision behind it Identity API and its own change log

    The identity system records a change. Nothing the gateway signed matches it. Perhaps the agent found a leaked token, or a second tool had its own.

    • API change log
    • Caller
    • Credential id

    AI’s part: It went round the gateway. Whether it was fooled or simply wrong does not matter here.

    Lab cases: B1B2

  2. The comparison flags it A scheduled job, run by security operations

    The job lines up the identity system's change log against the gateway's signed decisions. Every change should match one. The odd one out is a bypass alert, and approved changes made the same day are not flagged.

    • Change log
    • Signed decisions
    • Alert

    AI’s part: None. This job is plain code, so the agent cannot talk it out of anything.

    Lab cases: B2

  3. The policy switches the agent off The kill-switch policy, run by the gateway and vault

    If the change can be traced to one agent, its token stops working, its waiting approvals are cancelled, its lent credentials are revoked and the leaked token is revoked. If it cannot be traced, a person is alerted. The change itself is left alone.

    • Agent token
    • Waiting approvals
    • Vault leases
    • Leaked token

    AI’s part: Switched off. It can be brought back only by a named approver after review.

    Lab cases: B3B8

  4. Evidence first Security operations

    Before anyone cleans up, copy the logs, hash the copy and record who copied it and when. The chain of log lines shows any edit, and a saved anchor shows any cut.

    • Directory log
    • Gateway log
    • Vault log
    • Hash
    • Custody record

    AI’s part: May help to collect. Never holds the only copy.

    Lab cases: B10B12

  5. A person decides what to undo Agent sponsor and the head of IAM

    The sponsor and the head of IAM look at the evidence and decide whether to reverse the change. A named approver does it through the normal request path.

    • Decision
    • Named approver

    AI’s part: Cannot approve its own roll-back.

    Lab cases: B3

  6. Close the hole IAM engineering

    Rotate whatever was reached and find where it was lying. Make credentials work only from the caller they were lent to. Remove the network route. Add the case to the tests that run before every change.

    • Rotated credential
    • Caller binding
    • No network route
    • New test

    AI’s part: None.

    Lab cases: B1B4B5

  7. If a person was involved HR and legal, with a named case owner

    If the signal points to a person (for example heavy exports after a resignation notice), a case with a copy of the evidence goes to a named owner. HR and legal decide next steps, including whether to report to anyone. Accommodations and medical detail never go in the case.

    • Signal
    • Case owner
    • Evidence copy

    AI’s part: Raises a signal. Does not accuse, and cannot contact the police.

    Lab cases: B10B9B11

  8. Learn and practise Auditor and the response team

    Report the incident and the time it took. Add a drill every quarter. Watch the lists for the account states that matter: a leaver's account touched after it was disabled, a mover who keeps old access.

    • Time to switch off
    • Drill result
    • Watch alerts

    AI’s part: None.

    Lab cases: B6B7

I wrote the expected result for 12 new cases (B1 to B12) and saved them before writing any code, on 25 Oct 2026 at 01:07 IST. They cover a direct call with a leaked token, the same call when the API wrongly accepts it, the response policy, a missing network route, a lease used by the wrong caller or too late, a leaver’s account that is touched or switched back on, a mover who asks for new access too soon, a sponsor who leaves, a helper for a person who needs assistive technology, a possible offence by a person, requests for sensitive data, and a tampered audit log. What this does not show

  • The identity API, vault, network and log are small models I wrote. Real products, mutual TLS or token binding, and real networks will behave differently.
  • The agent does not really try to get round the wall. Each case makes it do the wrong thing and checks what stands in the way.
  • I wrote the guesses and the code, so “as expected” shows the rules do what I intended, not that I thought of every way round.
  • Changes made by other approved paths, such as the HR sync job, are not part of the comparison. If a bypass makes exactly the same change as a real request at the same moment, only the extra one is flagged.
  • The offence case only shows a signal reaching a person with evidence. What counts as an offence, what may be monitored and what a court accepts are for legal advice, not this lab.
  • The mapping below is my own reading, not legal advice and not a certification.
