How to read this page

Each case asks one question: does a bad outcome happen? in means it happens. out means it does not. I switch the controls on and off and write down what comes out.

The animated flows are teaching sketches. They show the order of events and where one control stops the attack. The list at the bottom is the evidence: the numbers come straight from the files my scripts wrote. Models are small rule simulations I wrote. They show whether a rule as written lets a case through. They do not show how any vendor product behaves.

The access chain: seven links

This is the framework the lab is built on. Every sign-in, and every action an agent takes for a person, passes through seven links. A case belongs to the link where its control sits. A weak link anywhere lets the bad outcome through, however strong MFA is at link 2.

1. Enrol and recover

Who can add, move or reset a way to sign in?

17 cases, 15 run. One control off lets it in: 10. Wrong guesses: 1.

Controls that decide it: Phishing-resistant enrolment, callback before reset, notice on change, delay on new methods.

2. Prove

How strong is the proof at sign-in?

14 cases, 14 run. One control off lets it in: 10. Wrong guesses: 0.

Controls that decide it: Phishing-resistant methods, number matching, rate limits, no weaker fallback.

3. Trust

Who vouches for the user, and is that voucher checked?

21 cases, 21 run. One control off lets it in: 17. Wrong guesses: 0.

Controls that decide it: Assertion replay and audience checks, exact redirects, PKCE, signing key care, pinned federation and CI/CD trust.

4. Decide

Does a rule cover this sign-in, and does it say the right thing?

33 cases, 32 run. One control off lets it in: 26. Wrong guesses: 3.

Controls that decide it: Default deny, no broad exceptions, report-only first, device and context signals that cannot be faked.

5. Issue

What does the token allow, for how long, and to whom?

16 cases, 16 run. One control off lets it in: 10. Wrong guesses: 1.

Controls that decide it: Narrow scope, short life, binding to the client, refresh rotation and a maximum age, no stored secrets.

6. Act

Is the sensitive action checked when it happens, not only at sign-in?

14 cases, 13 run. One control off lets it in: 12. Wrong guesses: 1.

Controls that decide it: Step-up checked by the server, every credential type covered, actions limited to what the human named and may do.

7. Watch and end

When something changes, does access actually stop?

15 cases, 13 run. One control off lets it in: 9. Wrong guesses: 0.

Controls that decide it: Revocation that reaches every token, continuous evaluation, expiry with the task, a named owner, logs that name the human.

Well known, and less talked about

What most teams already know

Phishing that relays a code, push approvals a tired user taps, replayed sign-in assertions, and help desk resets. Each has a clear fix in the models: a phishing-resistant method, number matching, one-time assertion IDs, a callback.

What gets less attention

An app that no rule ever covered. A token that never signs in, so MFA has nothing to check. A cloud trust policy that accepts any repository. A privileged call that never asks for fresh MFA. A client that trusts the sign-in server its own server names.

Where MFA is not the deciding control

In Run 5, the stolen integration token (W06) is decided by where the token can be used from. The privileged API call (W08) is decided by whether the check applies to every credential type, keys and service tokens included. Password reset (W07) is decided by whether it revokes refresh tokens.

What changes with AI agents

In Run 6, a sub-agent writing beyond the human’s rights (G03) is stopped only when the resource checks the human’s own permissions. An agent that outlives its project (G04) keeps working through credential rotation. An agent whose owner leaves (G05) is flagged but not removed. A cookie stolen after MFA (G07) gets past network checks if the attacker looks local.

What this does not show

  • The models are mine. I wrote them after the guesses, so a match shows my reasoning agrees with itself. Run 2 is the only run that caught me out.
  • Nothing here says how Okta, Entra, Ping or any other product behaves. It says whether a rule, as written, lets a case through.
  • The flows simplify. Real sign-ins have more steps than five arrows.
  • The three hand tests (E01 to E03) are not run. See Run 4.
