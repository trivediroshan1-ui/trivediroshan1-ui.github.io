CA and MFA lab · Guided route

The conditional access and MFA lab in 10 minutes

Three cases where MFA was on and the attacker still got in. For each one: what happened, a question, then the answer.

Last reviewed 15 November 2026. About three minutes a case. Nothing to install.

How to use this

  1. Read the case. Two lines on what happened.
  2. Make your own guess before you open the answer. That is how the lab itself works.
  3. Open the answer, then follow the link if you want the detail.

1. A stolen integration token

Case W06 · See it in the lab

An attacker steals a token that a third-party integration uses to reach your API. Every person in the company has MFA.

What to look at: On the framework page, open case W06 to see the controls and the script output side by side.

Does MFA stop the stolen token from reading customer records?

Show the answer

No. MFA is never asked: the token goes straight to the API. What decided the case was where the token can be used from. An address allow-list refused it.

Why it matters: MFA protects the sign-in step. A token that is already issued skips that step, so you need limits on the token itself.

2. An AI sub-agent writes where the person cannot

Case G03 · See it in the lab

A person asks an AI agent for help. The agent hands part of the job to a sub-agent, which writes to a system that person is not allowed to write to.

What to look at: The lab switched the controls off one at a time to see which one actually stopped it.

Which control stopped the sub-agent?

Show the answer

Only one held on its own: the resource checking the person's own rights.

Why it matters: An agent should never have more reach than the person it acts for. The place to check that is the system being written to.

3. A cookie stolen after MFA

Case G07 · See it in the lab

The person signs in with MFA. Afterwards, an attacker steals the session cookie and appears to be on the same network.

What to look at: Try it yourself: in the virtual lab, open run6.py, set attacker_same_network to True and run again.

Continuous evaluation watches the network. Does it catch the stolen cookie?

Show the answer

No. When the attacker appears to be on the victim's network, continuous evaluation misses it. Only binding the session to the device holds.

Why it matters: After sign-in, the session cookie is the identity. If it is not tied to the device, whoever holds it is you.
