Lab

Do conditional access, MFA and SSO controls hold up?

130 cases on made-up data: how people get past MFA, how single sign-on breaks, how recovery gets abused, and how conditional access rules fail when several controls interact, how agents and MCP tools sign in, and how AI agents get, pass on and keep access. I wrote my guesses first and locked them before any code. 6 of those guesses were wrong.

What came out

Read the video as text

MFA was on. The attacker still got in. I tested 130 sign-in cases to find where each control stops.

The rule: write the guess first. A Run 6 guess is shown with its SHA-256 hash, committed before any code existed. Change one word and the hash breaks, and a wrong guess stays wrong.

The framework: seven links every sign-in passes through. Enrol and recover (17 cases), prove (14), trust (21), decide (33), issue (16), act (14), and watch and end (15). A weak link anywhere lets the attacker through, however strong MFA is at link 2.

Case W06: a stolen integration token goes from the attacker to the API to the customer records, and MFA is never asked. An address allow-list refuses it. Where the token can be used from decided the case.

Case G03: an AI sub-agent writes where the person who asked cannot. Switching the controls on and off one at a time, only C, the resource checking the person’s own rights, held.

Case G07: a cookie stolen after MFA. When the attacker appears to be on the victim’s network, continuous evaluation misses it and only binding the session to the device holds.

What came out: 130 cases, 124 run on models, 118 guesses matched, 6 wrong. Run 1 41 of 41, Run 2 39 of 45, Run 3 16 of 16, Run 5 12 of 12, Run 6 10 of 10.

A perfect score on Run 1 told me the cases were too easy. I had written the models while knowing my own guesses. So Run 2 used several controls per case, and that is where I found out what I did not understand.

Run 3 covered the areas my first two searches missed. All 16 guesses matched, and I had predicted 2 to 4 would be wrong. That is the same warning as Run 1: I wrote the models after the guesses, so they agree with me. Run 3 shows that each case holds together step by step. It does not show how any product behaves.

The 6 guesses I got wrong

A notice is not a block (C01, C03)

I defined the bad outcome as “account taken and unnoticed”. A change notice or an alert makes any takeover noticed, so the controls that stop the takeover looked unnecessary. A notice tells you about an attack. It does not stop it.

Trusting a partner’s MFA (A05)

If you accept the home tenant’s MFA claim for guests, a weak home MFA satisfies your requirement and your own guest rule adds nothing. This depends on my assumption that the home claim is weak.

The control that decides the question (Z21)

I said refresh token lifetime did not matter. For “does the attacker still have access at 24 hours” it is the control that decides. Blocking the device code flow and requiring a compliant device matter for the first hour.

Scope of a control (X07)

Limiting trusted locations to the managed office network already stops an attacker on guest wifi. I thought the device rule was also needed.

A convention is not enforcement (A03)

Separate admin accounts are a habit. Blocking the admin group from non-admin apps is enforcement. I had the two the wrong way round.

What the guesses got right

Report-only mode protects nothing for an emergency account that never signs in during the test week (P05). Several controls were each enough alone: a phishing-resistant method, a compliant device at token use and token protection each stopped a stolen-session replay on their own (Z17). Pair checks for SMS fallback with SIM swap checks (C05) and registration protection with a device rule (Z22) failed only when both controls were off.

Cases I would have missed

A web search added 22 cases after my first catalogue. The biggest gaps: device code phishing, password-only tokens that skip MFA (ROPC), OAuth consent phishing, forged SAML assertions from a stolen signing key, and policies with no default deny. A second search added 16 more for areas I had skipped: step-up in privileged apps, federated sign-in, mobile and native apps, passkeys, and AI agents and MCP tools. Examples are a malicious federated domain that claims MFA was done, malware that gets a passkey assertion with no prompt, and an MCP server that accepts a token meant for another service. The register marks which cases came from search.

I checked the sources on 14 November

57 rows had a source I had not read, or I had marked them “verify”. I opened them. 30 are confirmed as worded, 10 are confirmed with a qualifier, 16 are partly confirmed and 1 is still open. Most of what I read is Microsoft Entra documentation, so those rows describe Entra, not every identity provider.

  • I had worded six rows more strongly than their sources allow (S08, S10, X09, Z09, Z19, Y08). I reworded them. No guess and no result changed.
  • One model claims more than the documentation. Z18 blocks a stolen token 10 minutes after it is revoked. Microsoft says the check covers Exchange, Teams and SharePoint Online with capable clients and can lag by up to 15 minutes. Read that result as holding only with a capable client and no lag.
  • Four chain tests (Z21, Z22, Y15, Y16) and the second half of Y04 are my own constructions. Each part has a source. The combination does not.
  • I left off dates that go stale, such as when Microsoft retires password-based SMTP (Z20).

What this does not show

  • These are small models of rule logic. They do not show how any vendor product behaves. Three cases need a real tenant, a hardware key and a person on the phone. I wrote my predictions for them on 14 November and committed them (commit 64c3573) before running anything. E01 and E02 are not run, and E03 needs volunteers. The Run 4 page has the details and how to run them yourself.
  • Several results depend on assumptions I chose and wrote in the code: the home tenant claim is weak, a reviewer keeps at most 5 exclusions, a change log is read within 7 days, 40 percent of users fall for a code lure. Change one and a result can change.
  • I made three mistakes in the test code, not in the guesses: bad test data in S06, a missing limit flag on Z01 and a wrong model for P11. I fixed them and kept the first-pass files in the record.
  • Run 3 models were written after the guesses. Two of its cases (Y06, Y08) rest on thin sources, so a match there says little about real behaviour.
  • Some sources are vendor blogs or research write-ups, not standards or the vendor’s own documentation. The register says which. I read at least part of the source for all 57 rows I had flagged, mostly as excerpts and not whole documents. One row, M06, is still open.
