Before you try any of this

  • Use a throwaway test tenant, never your work one. An enforced Conditional Access policy can lock you out. Keep one admin account excluded from every policy, and make sure you can reach its sign-in details.
  • A key reset erases every passkey on the key. Use a spare key that holds nothing you need.
  • Do not call a real help desk. Everything in E03 is made up.
  • No passwords, codes, tokens or tenant names in your notes. Blur screenshots.

E01: sign-in logs and a report-only policy

Setup: a test tenant where Conditional Access is available (licence terms change, check before you start). One test user with MFA registered. One policy that requires MFA for all users, all apps and all client apps, modern and legacy, set to report-only, with the excluded admin account.

  1. Does a normal browser sign-in show the report-only result for the policy on that sign-in row?
  2. Does a silent token renewal also carry a report-only result, and does it sit in a different log view from the interactive one?
  3. Does the portal’s CSV download have the per-policy result, so you can answer “who would have been blocked” from it alone?
  4. Does the interactive sign-in appear in the log within 5 minutes?
  5. Is a sign-in from a legacy-style client, such as an old mail protocol, visible in the log with the report-only result?

Write down: what each log row showed, how many minutes it took, and the export file name. Leave tenant data out of what you send.

E02: a hardware security key

Setup: one spare FIDO2 key, the same test tenant, one test user with an authenticator app registered as a second method. A passkey in a phone app is not a hardware key. If you use one, say so.

  1. Does enrolling the key and signing in with it work first time?
  2. With the key out of the picture and the authenticator app still registered, can the user still sign in?
  3. With the key as the only method and the key lost, can the user sign in alone, or do they need an admin?
  4. After an admin deletes the key’s registration, does the key stop working, and how long does a session that was already open keep working?
  5. Do repeated wrong PIN entries block the key, and does only a full reset bring it back, erasing the passkeys on it?

Write down: the key make and model, how many wrong PIN tries it took to block, and how long the old session lasted.

E03: a help desk call, role played

I am asking volunteers to play an IT help desk in a made-up company, one call each. I call as one of four callers. The desk has a one-page script that says to call back on the number on file before any reset, and to send a notice after any reset. They can refuse, end the call, or do the reset.

  • I decide how to count the results before the first call. A prediction matches if more than half of the desks for that caller type did what I predicted. A tie counts as wrong.
  • The script and the four caller descriptions go on this page after the calls, so nobody sees them early.
  • I will not record a call without asking, and I will not use anyone’s name.

It takes about 10 minutes. Tell me if you want to be a desk.

Run one yourself, and tell me if I was wrong

If you have a throwaway tenant, you can run E01 or E02 and tell me what happened. I will add it to this page marked as from a reader, with your first name or an alias if you want one. A wrong prediction goes on the page like any other. Send me what you found.

What this does not show

  • One tenant, one key or one volunteer on one day shows what happened in that setup. It does not show how every product behaves.
  • Portals and licence terms change. A result from today may not hold next year.
  • Volunteers for E03 come from my own subscribers, so they lean towards people interested in security. A real help desk may behave differently.
