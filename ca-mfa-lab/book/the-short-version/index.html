Who signs in? · Read this if you read nothing else

The short version

  • 130 cases in the register
  • 124 run on small models
  • 118 guesses matched
  • 6 guesses wrong, all in one run

I ran 124 of the 130 cases. 118 matched the guess I had locked before any code. Six did not, and all six were in Run 2, the run where each case had two or three controls working together.

The score is the least useful result. Four things I would tell a team that owns sign-in:

  1. MFA was often not the control that decided the outcome. A stolen integration token never triggers a sign-in. A password reset that does not kill refresh tokens leaves a stolen session alive. A recovery path weaker than sign-in lets an attacker enroll their own authenticator.
  2. The largest group of cases sits in link 4, Decide: a rule that does not cover the sign-in, an exception that grew, a legacy protocol that skips MFA. It holds 33 of the 130 cases and 3 of my 6 wrong guesses.
  3. For AI agents, the controls that decided Run 6 were plain ones: a named human owner, an identity that expires with the task, and a check at the resource against the human's own rights. Narrowing a sub-agent's token and rotating its credential did not decide anything.
  4. Each result rests on an assumption I chose. When I changed one assumption at a time, results flipped. A pass in this book holds only while its assumption holds.

Six cases need a real tenant, a hardware key, a real agent product or a person on the phone. They are written up as hand tests for anyone to run, with my predictions locked.
