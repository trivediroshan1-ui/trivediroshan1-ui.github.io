Who signs in? · Six wrong guesses, five kinds of mistake

What I got wrong

All six wrong guesses were in Run 2. Read together, they fall into five kinds of mistake. Each one is a habit I now check for before I write a guess.

I did not say what I was counting (C01, C03).

I defined the bad outcome as an account takeover that nobody notices. The change notice and the exclusion alert make any takeover noticed, so removing the SMS fallback or the exclusion review alone never produced the bad outcome.

I treated controls as independent (A05).

For guest sign-ins, trusting the home tenant's MFA claim means a weak MFA at home satisfies the requirement in mine. Adding my own guest MFA rule did not help, and with the trust on, all controls on still let the bad outcome in.

I picked the wrong control as the one that mattered (Z21).

I said refresh token lifetime did not matter. The bad outcome was the attacker still having access after 24 hours, which the refresh token lifetime decides. My wrong guess was in the pair test with two controls off together.

I did not think through a control's own scope (X07).

The trusted-network exception was limited to the managed office. Guest wifi in the same range was not trusted, so MFA was required and the attacker was stopped without the device rule.

I counted a convention as a control (A03).

Separate admin accounts are a habit, not enforcement. I had the two cases reversed: with only separate accounts nothing stops the admin account reaching a risky app, while the group block does stop the daily account.

One mistake in my own code

In the first pass of Run 2, my model said approval stops an unauthorised console change (P11). An unauthorised change skips approval by definition, so only the log can show it. I fixed the model and kept the first-pass script and results in the repository. This was a coding mistake, not a wrong guess, and I count it separately.
