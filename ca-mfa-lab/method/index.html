How the method works

I write what I expect before any code exists, lock it in a commit, then run the cases. Where I was wrong, the wrong guess stays.

  • Last reviewed 14 November 2026
  • Lab overview
  • What I got wrong
  • Made-up data only

The order is the method

  1. Write the case. A made-up company, the bad outcome, and the controls that could stop it. Why: If I do not say what I am counting first, I can talk myself into any result afterwards.
  2. Write my guess for each switch. One word each: in if the bad outcome happens, out if it does not. All controls on, all off, and each control off by itself. Why: A guess with no switch to flip cannot be wrong, so it cannot teach me anything.
  3. Hash the guesses file and commit it. After that I do not edit it. Why: A commit shows the order. The guesses came first.
  4. Only then write the code. A small model of the rule logic on made-up data. Assumptions I chose are written in comments. Why: Writing the code second means the code cannot shape the guess.
  5. Run it. Each case prints one line ending in OK, or MISMATCH where my guess was wrong. Why: A mismatch is the useful result. It shows where my picture of the controls was off.
  6. Fix my code, never my guess. If the code was wrong, I fix the code and say so. If the guess was wrong, both stay on the page. Why: Changing a guess after the fact would turn the record into a story I like.

How to read one case

Each case has up to three controls, A, B and C, and a bad outcome. The script tries every case with all controls on, with all off, and with each control off on its own. If switching off one control lets the bad outcome in, that control is doing the work. If no single switch does, either control alone is enough. Some cases also have a pair check, where two controls go off together.

The wrong guesses are the cases where my one-word answers and the script disagreed.

What the method does not show

These are small models of rule logic. They do not show how any vendor product behaves. Three cases need a real tenant, a hardware key and a person on the phone; the Run 4 page has the details. Several results depend on assumptions I chose and wrote in the code, such as a weak home tenant claim, a reviewer who keeps at most 5 exclusions, a change log read within 7 days and 40 percent of users falling for a code lure. Change one and a result can change.

Writing the guess first keeps me honest about my own thinking. It does not make the model right.
