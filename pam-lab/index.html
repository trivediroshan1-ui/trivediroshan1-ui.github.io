The privileged access map

One vendor-neutral architecture for privileged access, from the person or agent asking to the system they change, with every control station on the route. It covers the whole estate, maps four PAM vendors to it, and is tested in an open lab: 41 predictions locked before any code, 37 exactly right, and the four misses explained. Five of them were measured on real open-source software.

Roshan Trivedi · Independent practitioner guide · Last reviewed 28 Nov 2026. Lab run 28 Nov 2026. A general reference from public sources and my own lab, not a description of any employer's systems.

Every privileged action rides one of six lines

Pick a line. The token shows the route a request takes, station by station. The pale red zone is Tier 0: the PAM layer itself, which is why it is guarded like the domain controllers it protects.

Tier here means blast radius of a credential (Tier 0 = can change identity or the PAM layer itself). Organisation sizes are called small, mid-size and large in the build paths below, so the two never mix.

The lab: 41 predictions locked before any code, 37 exactly right

Each case is a small model of rule logic on made-up data (Kaveri Finance). It runs with no controls, with all three, and with each control switched off alone. A control is noticed when switching it off alone changes the counted outcome. The predictions were written, hashed and merged before the models existed. Roshan ran rounds 1 and 3 on his own Mac on 28 Nov 2026, and a second run gave identical numbers. What the run shows beyond the score

  • Real software agreed with 4 of 5 guesses. Round 4 found what the models predicted: sub-agents need their own tokens, per-task database credentials need revoking at the end, and an open SSH session keeps admin unless something re-reads the groups or ends it.
  • Layers hide in single-control tests. In seven rows no one control is noticed, yet two off together change the outcome. Test controls in pairs.
  • Plain code stopped the planted requests, not the AI's mode. In case 12 the code checks and the structured-fields limit did the work; recommend mode only set how many requests a person reads.
  • Alerts don't block. The outage alert in case 06 was never acted on in time, and an alert removed no admin rights in case 10.
  • JIT guards the PAM rules from outsiders, not from their own admins. Only a second person on each rule change stops an insider (case 13).
  • The weakest control is the sponsor's attestation. Changing how often sponsors attest wrongly moved nothing (round 3 case 03).

Why PAM now: attackers buy admin access, call the help desk, and go after the PAM tools themselves

Breach data

Credentials still carry the attack

Exploited flaws became the top way in (31%) in the 2026 DBIR, but stolen credentials are how attackers move sideways and climb. Admin access sells for about $1,300, and VPN logins make up 44% of what access brokers sell.

Verizon DBIR 2026, published 19 May 2026; SpyCloud and Delinea summaries.

Help desk

The reset is the new phish

In Q3 2026 Cisco Talos saw fake IT callers, armed with little more than names and email addresses, talk staff into remote sessions. One case ended in ransomware. In 2025 cases Coveware studied, attackers moved through help desk resets and MFA enrolment to privileged access.

Help Net Security on Talos IR, 30 Oct 2026; Coveware by Veeam.

The PAM layer

Remote access tools are targets

CVE-2026-1731, a pre-authentication remote code flaw rated 9.9, hit a widely used remote support and privileged remote access product in February 2026 and showed up in 16.7% of remote-tool incidents ReliaQuest tracked. Every vendor ships fixes; patch this layer first.

ReliaQuest threat spotlight, Dec 2025 to Feb 2026.

AI agents

Agents ask for shell, at machine speed

One vendor's telemetry counted 1.28 million shell commands requested from about 132,000 prompts in four weeks. In another vendor's survey, 87% had seen an AI tool reach data beyond its scope, and only 36% could always trace that access to a named person.

BeyondTrust Phantom Labs, Oct 2026; Delinea 2026 Identity Security Report. Vendor data.

Machines

Most privilege has no person behind it

Service accounts, API keys, pipeline identities and certificates outnumber people many times over. Nobody resets their password at a help desk, so nobody notices when one is stolen.

Idira 2026 Identity Security Landscape (vendor survey).

Market

The vendors are merging

Palo Alto Networks bought CyberArk (closed 12 Feb 2026) and renamed the products Idira in May. Delinea bought StrongDM (closed March 2026). Buyers choosing today pick a roadmap as much as a product.

Vendor announcements, 2026.

Sign-in strength for privileged access: SSO gets you in, the key you hold decides how safe it is

Strength against phishing and relay, for the sign-in that opens an admin session. Based on NIST SP 800-63B-4 (final, 31 July 2025) and CISA guidance. Round 1 case 11 tests these against each other.

Face ID and fingerprints aren't on the scale on purpose. NIST 800-63B-4 doesn't recognise a biometric as an authenticator by itself; it unlocks a key on the device, so its strength is the key's. SSO is one strong sign-in at the IdP; the PAM layer still asks again (step-up) before Tier 0.

Gartner sorts PAM by capability. I sort it by what fails.

What Gartner published

The 2026 Magic Quadrant for Privileged Access Management came out on 21 October 2026. Its public abstract says the market is evolving to manage privileged access "for machines, including AI agents". BeyondTrust, Delinea and Palo Alto Networks (Idira) each announced a Leader placement.

In Idira's reading of Gartner's 2026 Critical Capabilities, there are four use cases: password vaulting and sessions (PASM), endpoint elevation (PEDM), remote PAM, and PAM for machines. Just-in-time access is now expected, not optional.

The quadrant graphic and report text are Gartner's and are not reproduced here. Placements are taken from the vendors' own announcements.

My working theory DRAFT, for Roshan to approve

  1. Privilege is a length of time, not a role. Count hours of admin held, not number of admins.
  2. An alert is not a control. Only something that blocks, expires or removes counts. Rotation is not expiry.
  3. Controls hide each other. Switch each one off alone. The one whose absence changes nothing is either covered by another or was never tested.
  4. The PAM layer is Tier 0. Whoever can change the rules owns everything behind them.
  5. Rules check, people decide, AI recommends. Machine-speed requests go to rules; judgement goes to people; AI never decides Tier 0 alone.
  6. Write the guess before the test. Evidence you could have been wrong about is the only kind worth publishing.

Three build paths on the same map

Same architecture, different starting stations. Each path keeps what the previous one built.

Small or growing

One or two people own identity. Most systems are SaaS and cloud.

  • Vault and rotate every domain, cloud root and SaaS admin login; no shared passwords in chat or sheets
  • Passkeys or security keys for every admin
  • Vendors through a broker, never a VPN account
  • Cloud admin roles activated just in time
  • Two sealed break-glass accounts, tested twice a year

Leave for later: session farms, endpoint elevation at scale.

Mid-size, some regulation

A small IAM team, an ITSM tool, a SIEM, auditors once a year.

  • Everything on the left, plus
  • Session recording for Tier 0 and Tier 1
  • A ticket check that compares the system in the ticket with the system asked for
  • Endpoint privilege: elevate the app, not the user
  • Secrets out of code; pipelines sign in with OIDC, no static keys
  • Three SIEM alerts first: activation outside hours, new owner on a secret, admin granted outside PAM
  • An onboarding factory that brings accounts in by waves

Large, regulated, global

Several platforms, SAP or mainframe, plants, many vendors, AI agents.

  • Everything to the left, plus
  • Tier 0 isolation: admin workstations, separate admin plane
  • Vault pairs across regions with failover you actually test
  • SAP firefighter, JD Edwards, IBM i and mainframe brought into the broker
  • IT/OT boundary brokers with site-local break-glass
  • Agent registry, per-task tokens, gateway checks on every call
  • ITDR on the identity layer; PAM admins watched like domain admins
  • An operating model: a product owner, a platform team, the onboarding factory, a RACI and board-level KPIs
