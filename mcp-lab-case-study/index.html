MCP lab

Can a person stay in control of an AI agent?

I built a small approval gate for MCP tool calls, then tried to break it 76 ways. Here is what held, what did not, and what I still do not know.

The question

An AI agent can now search docs, read a repository, change a role and deploy to production. Some of those calls matter. I wanted to know: when a person says yes to one of them, can the agent only do exactly what was approved, once, and can anyone prove it afterwards?

policy gatea personexecutionaudit and unknownrefused

What I built

A small open-source gateway that sits between an agent and its tools, using MCP. Fixed rules score every call. Low-risk calls run. Risky ones wait for a person with the right role. The approval is tied to a hash of the exact request, works once, and expires. Every decision, including every refusal, goes into a hash-chained audit log. An AI analyst can write advice for the reviewer, but it cannot approve, deny or change the score.

How I tested it

Three ways: a real MCP client (the official Inspector) clicked by hand, a script that runs 76 cases against the real endpoint, and a browser lab where I can make a tool lose its reply. Every case has a line saying what I expected before I ran it. 81 use cases are documented; six are marked not done. The repo has 213 automated tests.

What held

  • A changed target, an extra argument, a look-alike letter or an invisible character: refused.
  • Reusing an approval, or two runs at the same instant: one runs, the other is blocked.
  • An expired approval, including after a real 11-minute wait: refused.
  • Editing a stored request or one audit event in the database: caught.
  • A lost reply: the work ran once, no second run was possible, and only a person who was not the requester could settle it.

What I got wrong

Six of my guesses were off on the first run. A trailing space did not matter. Hostile text was denied before a person saw it. A made-up reviewer was accepted. The status tool lagged behind the result tool, and an expired queue entry still looked pending. And one database edit let a request skip the human decision altogether.

The one real gap, and what I fixed

If someone could write to the database and flip a request to approved, it executed, and the audit log still looked valid, because nothing had been removed. The execute step trusted the status field. Now an approved request needs a stored human approval behind it, and a test covers it. I then closed the other open findings the same way: the status tool settles time before it answers, the text rules are written down and tested, an unsigned audit chain warns, and an over-long approval id is rejected. Reviewer identity is only partly addressed: an optional allowlist limits which typed names count, but names are still not proven.

What stays unsolved

People. When a reply is lost, a person settles the outcome, and the log holds whatever they say. I recorded “it ran” for something that never ran, and it was written down under my name. I approved 40 production deploys in under half a second with the same reason each time, and nothing slowed me down. A gateway cannot make a careless approver careful.

Not tested

Round two covered these: a second MCP client, real Claude Code on one laptop, a policy change while an approval is pending, a tool changed after approval, and harmless fields varying in a prototype. What is still not tested: real people reviewing at scale, a real sign-in, and any client other than the ones above. The full story is on the in-depth page.

Round two, in short

I went back with about 88 more scripted checks plus hand runs. One real gap was fixed (a tool changed after approval), the lab screen no longer hides direction marks, and a few limits are now written down. Read what I did, why, and what a firm can take from it.

How the numbers fit together

Three numbers about this lab appear on this site, and they count different things. I would rather spell that out than leave you to guess.

  • 210 scripted checks. What the three rounds ran against the gateway: 76 in round one, 88 in round two and 46 in round three. This is the number to quote for how much I tried.
  • 161 case cards. How those checks are written up on the portal: 75 cards for round one, 61 for round two and 25 for round three. There are fewer cards than checks because some cards cover a few closely related checks together.
  • 213 tests. The gateway’s own test suite in its repository, which protects the code as I change it. My Mac copy runs 210 of them, because the three tests for tool definitions are only in the repository version. Having 210 in both places is a coincidence. These are not the same 210.

If a page elsewhere on this site says “tests” next to 210, it means the scripted checks.

Honest limits

One run each, on my machines, with synthetic tools. This shows what this gateway did on these cases. It does not prove it secure.
