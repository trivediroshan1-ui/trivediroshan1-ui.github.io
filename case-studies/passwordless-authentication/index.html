Passwordless Authentication Rollout

How to move a workforce from passwords and weak MFA to phishing-resistant sign-in in risk order, and how to solve recovery, legacy apps and break-glass access on the way.

Credential Management Platform Owner & PAM Product Owner · Last reviewed 1 Oct 2026

The short version

  • Move people to phishing-resistant sign-in in risk order: privileged users first, then people who reach high-risk apps, then everyone else. One company-wide date puts the heaviest support load on the day you can least afford it.
  • Recovery decides whether the program works. If a lost key can be fixed with a text message or a password reset, an attacker will use that route instead of the strong one.
  • Keep a fallback during each wave and retire it only when adoption and help-desk data say the wave is stable. Legacy apps and break-glass accounts get named plans, not quiet exceptions.

The problem

Most workforces still sign in with a password and something extra: a text message code, an app code, or a push notification to approve. That is better than a password alone, and it is still phishable. A convincing fake sign-in page can collect the password and the code together and replay them to the real site. CISA’s phishing-resistant MFA fact sheet lists SMS and voice codes, push notifications without number matching and app one-time codes without number matching as forms of MFA that remain open to phishing, and it calls SMS and voice a last resort.

Phishing-resistant sign-in closes that gap. It also creates a project that is easy to get wrong. A blanket rollout can lock out the users least ready for it, while the accounts most worth protecting wait on the same generic timeline as everyone else. The administrator who can change every other account’s access ends up in the same queue as a part-time user of a low-risk tool.

So I start with practical questions. Who needs it most? What happens the day someone loses the device? Which applications cannot take a modern sign-in at all? And how will we know that people use the new method and do not drift back to the old one?

The terms, in plain words

  • WebAuthn. The W3C Web Authentication standard. It defines an API for creating and using public key credentials that are scoped to the site that created them. A credential can only be used with the same relying party it was registered with, which is why a look-alike site gets nothing useful.
  • Passkey. The FIDO Alliance describes a passkey as a FIDO authentication credential that lets a person sign in with the same process they use to unlock their device: a biometric, a PIN or a pattern.
  • Device-bound and synced. FIDO describes synced passkeys as credentials synced between a person’s devices through a cloud service, and device-bound passkeys as ones that never leave a single device, such as those on a security key.
  • Attestation. Evidence about the make and model of an authenticator, which a relying party can ask for at registration.
  • Authenticator assurance levels (AAL). NIST SP 800-63B uses these to describe how much confidence a sign-in gives. In the current revision, applications assessed at AAL2 have to offer a phishing-resistant option, and AAL3 requires a non-exportable private key and phishing resistance.
  • Authentication strength. Microsoft Entra’s name for a conditional access control that requires a set of methods. It has three built-in strengths: multifactor, passwordless and phishing-resistant. Phishing-resistant includes FIDO2 security keys, Windows Hello for Business or a platform credential, and certificate-based authentication.

I use Microsoft Entra as the worked example because its documentation is public and I checked it for this page. The same slots exist in other identity providers.

How a passkey sign-in fits together

There are four parts on the normal path and two on the side. On the normal path, the user and their authenticator, the identity provider, the conditional access and risk decision, and the resource. On the side, a recovery path and break-glass accounts. Logging runs under all of it.

Read the numbers in the picture in order. The authenticator signs a challenge for one site (1). The identity provider checks the signature against the public key it holds for that user (2, with the policy engine asking who, what and how risky). If the policy is met, the resource gets a token (3). If the user has no usable key, the policy does not fall back to a weaker method. It sends them to recovery (4), and recovery ends with a new passkey (5). Break-glass accounts stay outside the policy so a bad rule cannot lock everyone out, and every use alerts a person (6).

Two details from the Microsoft documentation shape the design. An authentication strength is evaluated after the initial sign-in, so it does not by itself limit which method a user starts with. And sign-in risk and user risk need Entra ID Protection. The per-user score I describe below is a separate, advisory input for planning waves. It never blocks anyone on its own.

The migration, in risk order

I run the move as waves. Each wave has a guardrail that has to hold and evidence that shows it held.

  1. Inventory methods and device posture

    Before setting an order, list which authentication methods each person has registered and what devices they sign in from. Readiness is uneven and assuming otherwise is how the least prepared users get locked out. In a directory such as Entra, the authentication methods activity report shows registration and usage by method, which gives a starting picture.

    GuardrailNo wave is planned from assumptionsEvidenceMethod and device inventory, agreed with the owners

  2. Score and order the waves

    Add an advisory risk score per user and device. It draws on things like privilege, access to sensitive apps, current method strength and device condition, and it can be rules, a model, or both. The score proposes an order. A person owns the order. Highest-risk accounts go first.

    GuardrailThe score advises and a named owner decidesEvidenceWave list with the owner’s sign-off

  3. Fix recovery before enrolling anyone

    Decide how a lost key, a new joiner and a locked-out user are handled, and test it, before the first wave. Recovery must end in a strong method again. The section on recovery below covers the design.

    GuardrailNo enrollment until recovery is written and testedEvidenceRecovery runbook and a test record

  4. Enroll two authenticators, with supervision

    Each person registers at least two, for example a security key and a passkey on a managed device, so one loss does not mean a recovery event. Registration is a sign-in that matters, so it needs a strong prior sign-in. Entra requires a user to have completed MFA within the past five minutes before registering a passkey (FIDO2).

    GuardrailTwo authenticators per person before enforcementEvidenceRegistration report by user

  5. Enforce by wave, report-only first

    Turn the phishing-resistant requirement on for one population at a time. Microsoft’s own guidance is to confirm a policy in report-only mode before switching it on. Exclude the break-glass group deliberately and document why.

    GuardrailReport-only results reviewed before enforcementEvidencePolicy impact review and the exclusion record

  6. Keep the fallback, and watch the data

    During each wave a fallback path stays available. I watch adoption, sign-in failures and help-desk tickets for that population. If tickets climb or people keep using the old method, the wave is not done, whatever the calendar says.

    GuardrailFallback stays until the exit criteria are metEvidenceAdoption and ticket data per wave

  7. Retire the weak methods for that population

    Once adoption and ticket data confirm the wave is stable, remove passwords and weak methods for those users and take the fallback away. Then move to the next wave. This is how the highest-risk accounts end up on phishing-resistant sign-in ahead of the general population, and how help-desk load spreads across waves instead of landing on one cutover date.

The recovery problem

A strong sign-in method is only as strong as the way back in. If a user who loses a key can reset it by answering a text message, the text message is now the real sign-in. NIST SP 800-63B-4 treats recovery as its own topic (Sec. 4.2), including saved recovery codes and a notification to the user after recovery (Sec. 4.2.3). I did not verify the full list of recovery methods and requirements, so read that section before you write yours.

What I design for is a recovery that repairs the strong method and does not step around it. Four cases come up again and again.

  • Lost or broken device, second key available. The person signs in with the other authenticator and registers a replacement. This is the cheap case, and it is why I want two authenticators for everyone before enforcement.
  • Lost device, no second key. The help desk verifies identity with a process that does not rely on anything the attacker could phish, such as a video call with the manager present, or in person. Then it issues a time-limited pass. In Entra, a Temporary Access Pass is a time-limited passcode, configured for one use or several, that lets a user onboard passwordless methods and makes recovery easier when a strong method is lost. Its lifetime is configurable, with a default of one hour, and a single-use pass needs the registration finished within 10 minutes of sign-in. The user registers a new passkey straight away.
  • New joiner. The same pass, issued at day one after HR and the manager confirm the person, ideally handed over alongside a security key. The first thing a new joiner does is register two authenticators.
  • Privileged user. I raise the bar: in person or two-person approval, a shorter pass, and an alert to the security team. A recovery for an administrator is a high-risk event and gets treated as one.

The Entra documentation notes that a Temporary Access Pass cannot be used with the Network Policy Server extension or the AD FS adapter, so check where else a pass will not work. Whatever the product, the pass is itself a credential. It is short-lived, issued by a verified process, sent to a verified channel, and logged, and the user is told when it is issued.

Device-bound or synced, and what attestation changes

The choice between device-bound and synced passkeys is a risk decision. NIST SP 800-63B-4 says syncable authenticators cannot be used at AAL3 because the private key has to be exportable, and it allows them at AAL2 and below. That gives a simple starting rule: device-bound for people and apps that need the top level of assurance, and synced passkeys where AAL2 is the target and the convenience is worth it.

Microsoft’s passkey documentation adds three practical points. When attestation is enforced at registration, Entra can verify the make and model of the authenticator against trusted metadata. When it is not enforced, Entra cannot guarantee any attribute of a passkey, including whether it is synced or device-bound. And the documentation advises treating synced passkeys as phishing-resistant credentials with the same security posture as other unattested authenticators. Its synced passkey page adds that synced passkeys do not support attestation, and suggests device-bound passkeys such as security keys or passkeys in Microsoft Authenticator for admins and highly privileged users.

So the policy I write has two profiles. Privileged users and the highest-risk apps require attested, device-bound authenticators. Everyone else may use synced passkeys. Entra supports this with passkey profiles, which are named sets of rules that govern registration and sign-in for targeted groups, and it allows up to three of them, including the default. Two cautions from the same page. Key restrictions, which allow or block authenticators by AAGUID, apply to both registration and sign-in, so removing an allowed AAGUID stops people who registered that model from signing in. And attestation is checked only at registration, so users who registered without it are not blocked later if you turn it on.

Legacy apps that cannot do modern sign-in

Every program meets the application that only knows a username and password. I handle these in the open. List them, give each an owner, and pick one of four routes.

  • Put it behind the identity provider. If the app can speak SAML or OpenID Connect, move it to single sign-on so the policy applies. OMB M-22-09 asks that MFA be enforced at the application layer, not only at the network layer.
  • Upgrade or replace it. CISA’s fact sheet advises a plan to either upgrade systems that do not support MFA or migrate away from them, and to escalate the risk of any system that does not support MFA to senior leadership. I follow that literally. The owner of the risk gets the decision in writing.
  • Contain it. Where neither is possible yet, narrow who can reach it, put it on a restricted network path, scope its accounts and monitor its sign-ins more closely.
  • Block legacy protocols where you can. In Entra, legacy authentication clients, such as POP3, IMAP4 and SMTP, do not support MFA or pass device state, so conditional access grant controls like requiring MFA or a compliant device block them. Check what depends on them first.

Anything left over goes on the exception register with an owner, a reason, a compensating control and an end date, reviewed on a rhythm. An exception with no end date is a decision nobody made.

Break-glass access during the move

Emergency access accounts are the part of a passwordless program that people forget until a policy locks them out. Microsoft recommends two or more emergency access accounts, authenticated with a passkey (FIDO2) or certificate-based authentication, using phishing-resistant methods that differ from those of the normal admin accounts. It also recommends excluding a dedicated group from conditional access policies that block or restrict sign-in, monitoring their sign-in and audit logs with alerts, and testing them at regular intervals, at least every 90 days.

The interaction I plan for is simple. Each new wave and each new policy gets a check that the emergency accounts still work and still alert. Break-glass accounts belong in the first wave, because they are privileged by definition. The full design is in Break-Glass Access.

The help-desk process

The help desk is where recovery meets people, so it needs its own script. The agent proves identity with the agreed method, issues a time-limited pass, and never reads out or resets a password as a shortcut. The ticket records who verified whom, how, and when the pass was issued. A recovery for a privileged account goes to a second person. After recovery the user gets a notice on a channel the requester does not control, and the old authenticators are reviewed and removed if they are lost.

Worked example

This is an illustration of the flow, not a specific event or company.

An infrastructure administrator, before and after wave 1

Before

  • Signs in with a password and approves a push notification on a phone.
  • Has one registered method, so a lost phone means a help-desk call.
  • Recovery over the phone with a few personal questions.
  • Sits in the same wave as every other user.

After

  • Signs in with a security key and a PIN. Phishing-resistant strength is required for admin roles.
  • Has a second key stored securely, so a lost key is a swap.
  • If both are lost: video call with the manager, then a short-lived pass issued by a second person, then a new key at once.
  • The recovery alerts the security team and notifies the admin.

The fallback stayed in place for this group for the first weeks and was removed only after adoption and ticket data looked stable. The general population follows the same flow in a later wave, with synced passkeys on managed devices.

How I phase it

  1. 1. Inventory and designList methods, devices and legacy apps, and write the recovery design, the policy profiles and the wave order.Done whenThe inventory is agreed with its owners and recovery is written down.
  2. 2. PilotRun the identity team and a few volunteers through enrollment, sign-in, loss and recovery.Done whenEvery recovery case has been tried at least once and the runbook has been corrected.
  3. 3. Privileged users and break-glassEnroll administrators on device-bound authenticators and enforce phishing-resistant strength for admin roles.Done whenAdmin roles cannot sign in with a weak method and the emergency accounts have been tested.
  4. 4. High-risk apps, then everyoneRequire phishing-resistant strength for the sensitive apps, then widen to the whole workforce wave by wave.Done whenEach wave meets its exit criteria and its fallback is removed.
  5. 5. Close the long tailResolve or date every legacy app and special case, and remove old methods from the tenant.Done whenWeak methods can no longer be registered and the exception register is short and dated.

Measuring adoption

I want measures that show whether people use the strong method as well as whether they registered it. In Entra the authentication methods activity report has a registration view, which shows how many users are capable of passwordless authentication and how many are registered by method, and a usage view, which shows sign-ins by authentication requirement and by method. Other identity providers offer similar reports.

  • Registered and capable. Share of each wave with a phishing-resistant authenticator, and with two.
  • Actually used. Share of each wave’s sign-ins done with the phishing-resistant method, and how many users still sign in with a weak one.
  • Privileged coverage. Admin roles with a device-bound authenticator and no weak fallback.
  • Support load. Credential-related tickets per wave, time to recover, and recoveries that needed a second approver.
  • Long tail. Legacy apps and exceptions open, and how many have an end date.

I read these by wave. A single company-wide number hides the cases that matter.

  • One owner for the order. The risk score is advisory. A named person approves the wave list and can change it.
  • Exit criteria written before each wave. Adoption and ticket thresholds are agreed first, so nobody argues about them mid-wave.
  • Changes to recovery are policy changes. Loosening the recovery path goes through the same approval as loosening sign-in.

What tends to go wrong

  • Recovery becomes the weak door. Teams harden sign-in and leave password reset or phone verification in place. Attackers go to whichever door is easier.
  • Enforcing too early. A strict policy that was never run in report-only mode catches the shared mailbox, the service desk tool or the executive assistant’s old laptop.
  • Treating synced and device-bound as the same. Without attestation you cannot tell them apart, so the policy cannot treat them differently.
  • The fallback never goes away. If weak methods stay registered, an attacker can ask for them. Users, too, will drift back to the familiar one.
  • Legacy apps on an endless exception. Without owners and end dates, the long tail stays long.

What I have learned to do differently

These are habits I keep, not a checklist from any one project.

  • Start from the data, then talk to the owners. I inventory methods and devices first, and then walk the list with the people who own each group. The order comes from that conversation, with the score as an input.
  • Write recovery first. I used to treat it as a support detail for later. Now I write it before the first enrollment, and I try to break it in the pilot.
  • Ask for two authenticators from day one. It is easier to ask at enrollment than to chase people after the first loss.
  • Make the fallback expire. Every fallback gets a review date and a named approver when I create it.
  • Treat the help desk as part of the design. I sit in on calls, read the tickets and change the script, because the control lives there as much as in the policy.
  • Test the emergency accounts every wave. I do it even when the last test passed. A new policy is a new chance to lock them out.

The broader approach, from first conversation to last training session, is in How I Run a Privileged Access Program.
