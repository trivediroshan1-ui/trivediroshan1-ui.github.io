Agentic AI Identity Governance

AI agents request permissions, spawn sub-agents and chain actions across systems while they run. This is a governance model for an identity that changes shape in the middle of a task: one owner per agent, a short-lived credential per task, a decision on every action, and a person for the risky ones.

Credential Management Platform Owner & PAM Product Owner · Last reviewed 1 Oct 2026

The short version

  • An agent is a non-human identity that makes choices at runtime. Give it its own identity, a named human owner, and no standing access.
  • Issue one short-lived credential per task, scoped to one tool, and decide again on every action. Actions that are expensive to undo wait for a person.
  • Record who the agent acted for, not only that it acted. Keep a switch that turns the agent off, and practise using it.

The problem

Agent frameworks let an AI pick up scopes, call APIs and launch sub-agents as it goes. The identity a workflow ends up using is decided while it runs, long after anyone provisioned it. Most Identity and Access Management (IAM) stacks assume the opposite: a role is assigned once and holds, and an access review treats a snapshot as a fair description of the account. Neither assumption survives an agent that can ask for a new capability halfway through a job.

In practice the first agents in a company tend to arrive through the side door. Someone creates an API key, pastes it into a framework, and the agent starts working under that person’s authority or a shared service account. Nobody registered it, nobody owns it, and the logs show a human name next to actions that person never saw. I wrote about the sharing side in One Key, Every Agent.

I am not arguing for fewer agents. AI is the future of a lot of this work, and humans cannot be replaced in it. The two work best together, with security, governance, monitoring and collaboration around them. An agent should be easy to adopt and easy to stop, and a person should be able to see what it did and say no when the action is hard to reverse.

What is being governed

Two questions come up in every conversation about agents. Who is the agent, and for whom is it acting? The first is identity and the second is delegation. Keeping them apart makes the design easier.

  • The agent has its own identity. It is a non-human identity, like a service account or a workload, with an entry in a registry. It does not borrow a person’s login or share a key with other agents.
  • The agent has a named owner. One accountable person, with a backup, who can explain what it is for and decides whether it keeps running. A team mailbox does not count.
  • The agent acts on behalf of someone or something. A user who asked for the task, or a business process that triggered it. That principal is recorded next to every action.
  • Sub-agents get less, never more. If an agent starts another one, the child gets its own identity or a child credential with a narrower scope and a shorter life than the parent’s.

OAuth already has the vocabulary for delegation. RFC 8693 (OAuth 2.0 Token Exchange) separates impersonation, where one party becomes indistinguishable from another, from delegation, where the actor keeps its own identity and acts for someone else. Its act claim names the acting party inside a token, and nested claims can show a chain of actors. For agents I want delegation. A trail that says “this agent, for this user” is far more useful than one that says “the user”. The MCP authorization section I read does not list RFC 8693, so using it in a broker is my suggestion and MCP does not require it.

How it fits together

The agent asks to act. A policy decision point checks the request against the registry and the rules. A human approves anything above the risk threshold. A credential broker issues a short-lived token for exactly that action. The tool, usually an MCP server, validates the token and acts on the target system. A log records each step, outside the agent’s reach.

One action, start to finish

The steps follow a single action through the diagram. Each has a guardrail, which the design requires, and evidence, which you can show an auditor afterwards. A guardrail with no evidence is a hope.

  1. The agent asks to act

    The agent authenticates as itself and states the task, the tool it wants and the principal it is acting for. With no registry record, or a suspended one, the request ends here. This is the zero standing privilege starting point: the agent holds no access between tasks.

    GuardrailNo registry record or no owner, no accessEvidenceRegistry entry and authentication log

  2. Policy decides, every time

    The decision point looks at who the agent is, the task, the tool and arguments, the risk tier and what already happened in this task, then decides again on the next action. This is continuous authorization: a new permission request or sub-agent is judged when it appears, and the next review cycle is too late. NIST SP 800-207 has the same idea for zero trust: access per session, with authorization strictly enforced before access is allowed.

    GuardrailDeny by default, evaluated per actionEvidenceDecision record with the policy version used

  3. A person approves the risky ones

    Above the risk threshold the action pauses and goes to an approver, who sees the exact action and its parameters. The approval is bound to that action and expires quickly. This is the pattern from my MCP Human Approval Gateway lab: autonomy stops where a wrong action is expensive to reverse.

    GuardrailApproval tied to exact parameters, short expiryEvidenceApprover, time, parameters shown, outcome

  4. The broker issues a short-lived token

    If the action is allowed, the broker issues a credential for this tool only, with the narrowest scope that does the job and a lifetime measured in minutes. Where delegation matters, the broker mints a token that names both the user and the agent.

    GuardrailOne tool, narrowest scope, short lifetime, audience set to the target serverEvidenceIssuance log: subject, actor, audience, scope, expiry

  5. The agent calls the MCP server

    The server checks that the token was issued for it and that the scope covers this operation. If the scope falls short, it answers with an insufficient scope error, which sends the agent back to step 2. It never widens anything on its own.

    GuardrailServer rejects tokens issued for any other audienceEvidenceServer access log with token audience and scope

  6. The server acts with its own credential

    The server calls the target using its own credential and passes along who the agent is acting for, in whatever form the target accepts. It does not forward the agent’s token. The target still runs its own authorization, so a confused or manipulated agent meets a second check.

    GuardrailNo token passthrough, downstream authorization stays onEvidenceTarget-side log that links back to the agent’s call

  7. Log, correlate, expire

    Every step writes to a log that the agent and its owner cannot edit, and a correlation ID ties request, decision, approval, token and call together. When the task ends the token expires. Granted permissions are compared with what the agent really did, so drift shows up as a signal and not as a surprise after an incident.

    GuardrailLogs held outside the agent’s reach, token expiry as the default stopEvidenceOne correlated trail per task, plus a permissions-versus-behaviour report

Example: an operations agent and a stuck export job

This is an illustration, not a specific event.

An operations team registers an agent for failed batch jobs. Its owner is the team lead, and it is registered for three tools: read job status, restart a job, and clear temporary files. A user asks it to fix a stalled overnight export.

  • Reading job status is low risk. Policy allows it and the broker issues a read-only token that lives a few minutes.
  • Restarting the named job is medium risk. Policy allows it for that one job, and the token is scoped to that restart.
  • Clearing temporary files is high risk, because deletion cannot be undone. The request pauses, and the approver sees the exact path pattern and how many files it matches. They approve once, for that pattern, and the approval expires.
  • Halfway through, the agent asks for a database administration scope. Policy refuses, because that tool is not on its list. Getting it means the owner changes the registration, and that goes through review.

Before

  • The agent runs on a personal API key that was pasted into a config file.
  • It can touch everything its creator can touch, all the time.
  • The logs show the creator’s name next to every action.
  • Nobody can say who owns it or when it was last reviewed.

After

  • The agent has its own identity and a named owner.
  • Each action gets a short-lived token for one tool.
  • The deletion waited for a person who saw the exact files.
  • The log shows the agent, the user it acted for, the approver and the result.

MCP connections and what the specification gives you

Many agents reach their tools through the Model Context Protocol (MCP), so I start with its authorization section. I read the current draft on modelcontextprotocol.io, its security best practices page and the tools page of the 2026-07-28 revision. The specification changes, so check the revision you deploy. These are the points that matter for governance.

  • Authorization is optional, and defined for HTTP transports. Implementations that use stdio should take credentials from the environment instead. A local stdio server therefore sits outside any broker unless you choose to wrap it. My reading is that local servers are a governance gap to plan for.
  • An MCP server is an OAuth resource server. The client is an OAuth client. The server must publish OAuth 2.0 Protected Resource Metadata (RFC 9728), which tells the client which authorization server to use.
  • Tokens are bound to one server. Clients must send the resource parameter from RFC 8707 (Resource Indicators for OAuth 2.0) in both the authorization request and the token request, naming the MCP server the token is for. Servers must validate that a token was issued for them and must not accept or pass on other tokens.
  • Scopes can grow when needed. A server can answer with a 403 and an insufficient_scope challenge that names what the operation needs, and the client can start a step-up authorization. The security guidance adds that servers should log elevation events with correlation IDs and avoid wildcard scopes. Step-up is the protocol’s version of deciding again at the moment of need, which is where my policy decision plugs in.
  • Token passthrough is forbidden. The security page explains why: it bypasses controls that depend on the token audience, and downstream logs then show a different identity from the one that made the call. That is an audit argument as much as a security one.
  • A person should be able to say no. The tools page says there should always be a human in the loop with the ability to deny tool invocations, that clients should prompt for confirmation on sensitive operations and show tool inputs first, that servers must implement access controls and rate limit, and that tool annotations are untrusted unless they come from a trusted server.

The authorization section leaves the authorization server implementation out of scope. It says nothing about who owns an agent, which actions need approval, how to record delegation or how to retire an agent. Those pieces sit around the protocol, and they are what this page is about.

Kill switch, revocation and lifecycle

A short token life is the cheapest way to stop an agent, because access ends by itself. It is not enough alone, so I design the stop in layers and test each one.

  • Suspend the agent in the registry. The broker reads the status before issuing anything, so no new tokens come out.
  • Let tokens run out. With lifetimes in minutes, existing access fades quickly. Anything longer-lived, such as a refresh grant, is revoked at the authorization server. Whether an issued access token can be killed early depends on the token type and on whether servers check its status, so I confirm that per system.
  • Block it at the tool. The MCP server or its gateway keeps a deny list keyed on the agent ID.
  • Rotate what sits downstream. If the agent or its credentials may have been exposed, rotate the secrets the tool uses to reach the target systems.

Then the lifecycle, which has three moments.

  • Register. The owner states the purpose, tool list, principals and risk tier. A reviewer approves the registration before the broker issues anything, and it carries an expiry date.
  • Review. On a rhythm tied to the risk tier, the owner confirms the agent is still needed and compares granted permissions with what it did. Unused permissions are removed. The drift report from step 7 earns its place here.
  • Retire. When the project ends or the agent goes quiet, it is suspended, grants are revoked, downstream credentials are rotated, and the record is kept with its logs. An owner who leaves triggers a reassignment, and with no taker the agent is suspended.

How to build it without stalling

I would not do all of this at once. Each phase is useful on its own, and the order follows the risk.

  1. 1. Find the agents and name the ownersInventory what already runs, including agents on personal keys. Create the registry and give every agent an owner. Retire what nobody claims.Done whenEvery known agent has an owner and a purpose on record.
  2. 2. Put a broker in front of the first toolsPick one or two tools with real impact. Issue short-lived, audience-restricted tokens through a broker and take the long-lived keys out of the configuration.Done whenThose agents hold no standing credential for those tools.
  3. 3. Add per-action policy and approvalDefine risk tiers. Allow low-risk reads, require a person for hard-to-undo actions, and bind each approval to its parameters.Done whenA deletion or payment cannot go through without a recorded approver.
  4. 4. Record delegation and watch for driftMake every token and log line carry the agent, the principal and a correlation ID. Report granted permissions against observed behaviour.Done whenYou can answer “which agent did this, for whom” from the logs alone.
  5. 5. Practise the stop and the lifecycleRun a drill that suspends an agent and measures how long access takes to end. Add expiry dates, owner attestation and retirement to the routine.Done whenA drill has been run and its result recorded, and registrations expire when nobody confirms them.

Governance: who owns what

RoleOwns
Agent ownerThe agent’s purpose, its tool list, requests for more scope, the periodic confirmation and its retirement
ApproverThe yes or no on actions above the threshold. Sees the exact action, can refuse, and is never the agent
Platform teamThe registry, the broker, the policy engine and the log pipeline: availability, upgrades and integrations
MCP server and tool ownersThe tools they expose, their scope definitions, audience validation and the credentials they use downstream
Principal (the person or process delegating)The authority the agent borrows. Their identity is recorded, and their access is the ceiling for what the agent can do for them
Security architectureRisk tiers, approval thresholds, token lifetimes and the exception criteria
Internal auditIndependent checking, separate from those who run the controls
  • The owner and the approver are different jobs. For the top risk tier I want them to be different people, so that the person who set up the agent is not also the one who waves its riskiest actions through.
  • Measure coverage and age. Useful measures: share of known agents with an owner, long-lived credentials held by agents, time since last review, share of high-risk actions with a recorded approval, and the result of the latest drill.
  • Exceptions have owners and end dates. An agent that cannot use the broker goes on a register with a reason and a date.

What tends to go wrong

  • Approval fatigue. If everything needs a click, people click through. Keep approvals for hard-to-undo actions and show the exact action.
  • Broad scopes granted up front. It is easy to ask for everything once and avoid later prompts. The MCP security guidance lists wildcard and omnibus scopes as a common mistake, and a general-purpose client with no scope challenge may fall back to requesting everything the server lists, so the server side matters here.
  • The MCP server as a pass-through. Forwarding the caller’s token looks simpler. It erases the audit trail and breaks the audience boundary.
  • Logs that name the person and hide the agent. If delegation is not recorded, the human gets blamed for, or credited with, actions they never saw.
  • Sub-agents that inherit everything. A child that carries the parent’s full rights turns one compromise into a chain of them.
  • The prompt treated as a control. An instruction to the model is a request. The OWASP guidance on excessive agency is clear that authorization belongs in the downstream system and not in the model’s judgement.
  • Local servers that nobody registered. Servers started on a laptop through stdio sit outside the broker. Decide what is allowed there early.

What I have learned to do differently

These are habits I keep with any new kind of non-human identity. They come from how I run access programs and from my own reading and testing, and they are not a record of any one project.

  • Start with the owner. I used to start with the technology. Now my first question about any agent is who answers for it. Everything else, from scope to review, hangs off that name.
  • Treat every agent as a new hire with a narrow job. I write the job in one sentence, give it only the tools it needs, and expect to be asked for more access later, with a reason.
  • Read the protocol before designing around it. I check what the MCP authorization section requires and what it leaves open before I decide what my broker has to do. That saves me from rebuilding what the protocol gives me and from assuming it covers things it does not.
  • Make the approval screen honest. If I would not understand the request when tired, the screen is wrong. It shows the exact action, the target and what cannot be undone.
  • Test the stop before I need it. I want a measured answer to “how long until this agent can do nothing”, from a drill.
  • Check the sources and label what I inferred. When a mapping is my own, as with the AI RMF, I say so in the text.
