AI governance · Non-human identity

Every agent gets a name. Almost none get their own key.

The quickest way to connect an AI agent to five systems is to hand it one long-lived credential. This is what that costs, and how I would issue credentials to agents instead.

Independent research & control design · Last reviewed 1 Oct 2026

The short version

  • When an agent runs on a person’s token or a team’s shared key, the logs name the wrong party, the access is wider than the task, and the secret tends to end up in prompts, config files, logs and tool output.
  • The alternative is simple to say. Each agent has its own identity. A broker issues a short-lived credential for one task, scoped to one target, on behalf of a named user. The model never sees the secret.
  • Every record then shows two names: the agent that acted and the person it acted for. That is what an auditor, and an incident responder, will ask for.

The problem

Agents are easy to start and hard to account for. A developer wires one into a ticketing system, a code host, a data store and a cloud account. The fastest way to make that work is to paste in a credential that already works: a personal access token, a team service account, or an API key from a shared vault entry. It works in a demo. It keeps working long after the demo.

I see five things go wrong with that shortcut, and they feed each other.

  • Attribution is lost. The target system sees the person’s name, or the team account’s name. Nothing says an agent acted, which agent it was, or what it was asked to do. If three agents share one key, even the agent’s own team cannot tell them apart.
  • Access is wider than the task. A person’s token carries everything that person can do. An agent that only needed to read tickets can now delete them, read the finance share, or push to production. OWASP lists excessive functionality, excessive permissions and excessive autonomy as the three root causes of what it calls excessive agency. A borrowed human credential supplies the second one for free.
  • Secrets leak into places they should never be. A key in the system prompt can be repeated back by the model. A key in a config file lands in version control. A key echoed in a tool result lands in the conversation history and the trace store. OWASP’s guidance on system prompt leakage says sensitive data such as credentials and connection strings should not be in the system prompt at all.
  • Tokens live too long. A credential made for a demo is rarely retired. Nobody remembers it exists until it is used by someone who should not have it.
  • One leak means every system. Because the same key reaches everything the agent touches, a single exposure, whether from prompt injection, a log line or a stolen laptop, is an incident in all of those systems at once.

None of this is new. Shared accounts and long-lived keys were a problem long before agents. What agents change is the speed and the number. They make many calls, they chain tools, and they read untrusted text that can steer them. The credential that was risky in a script is riskier when a model decides what to do with it.

Why I do not treat this as theory

The clearest public example I found is the 2025 compromise of tokens issued to a third-party integration. Between 8 and 18 August 2025, a group tracked by Google Threat Intelligence as UNC6395 used stolen OAuth tokens for the Salesloft Drift integration to pull data out of customers’ Salesforce instances. Google reported being aware of more than 700 potentially affected organizations. By 20 August, Salesloft had started working with Salesforce to revoke all active access and refresh tokens for the Drift application. The attackers went through the stolen data looking for secrets such as AWS access keys, passwords and Snowflake access tokens, which is a reminder that credentials pasted into records and notes become a second leak.

That incident was about a vendor integration, not an agent run inside someone’s own company. I include it because the shape is the same: a token that was trusted broadly, kept alive, and valid across many customers. Revoking everything was the only fast way to stop it. A design where each connection had its own token, scoped and short-lived, would have made the blast radius smaller and the revocation more precise.

Two ways to connect the same agent

Both designs get an agent talking to the same systems. The top lane is the shortcut. The bottom lane gives the agent a name of its own and puts a broker between the agent and every credential. The broker is a vault or secrets service that can mint or hand out credentials by policy and write the log. In the second design the model decides what it wants to do. It does not hold the key that does it.

Two details in the lower lane carry most of the weight. The token goes to the tool layer that makes the call. It does not pass through the model’s context. And the target system checks the token on its own. OWASP’s guidance on excessive agency says to implement authorization in downstream systems rather than relying on the model to decide whether an action is allowed.

Acting for a person without becoming that person

The hard part of the better design is how an agent acts on a user’s behalf and still leaves both names in the record. OAuth has a vocabulary for this. RFC 8693, the token exchange specification, separates two ideas. With impersonation, principal A is given all the rights of principal B and is indistinguishable from B in that context. With delegation, A keeps its own identity, and any action is understood to be taken by A representing B.

For agents, delegation is the one I want. Impersonation is what a pasted personal token does: the log says Priya did it. Delegation keeps the agent visible. RFC 8693 expresses this with the act claim, which identifies the acting party to whom authority has been delegated, and nested act claims can show a chain of prior actors. A may_act claim states that one party is authorized to become the actor for another. The token request can carry an actor_token that represents the acting party.

I do not think every environment needs to implement RFC 8693 literally. Some identity providers offer their own on-behalf-of flows, and some target systems only accept static API keys. The test I apply is the one the RFC describes: after the action, can I see both who acted and who they acted for, and can the agent be switched off without touching the person’s account?

The MCP authorization specification adds two useful rules for tool servers. Tokens are bound to their intended audience with the RFC 8707 resource parameter, and a server must accept only tokens issued for it. If it calls an upstream API, it must not pass through the token it received. It uses a separate token issued by the upstream authorization server. The same specification says authorization servers should issue short-lived access tokens to limit the damage of a leak, and that local stdio servers should read credentials from the environment instead of following the HTTP flow. That last point matters: an environment variable is still a secret sitting next to the model’s tools, so I treat it as the weaker option and keep it out of the model’s context.

Issuing a credential to an agent, step by step

This is the path I would put in front of a team that wants to launch a new agent. Each step has a guardrail that stops a specific mistake and a piece of evidence you can show later. It assumes a person still owns the agent, and that risky actions still go to a person for approval. Agents do a lot of useful work, and the people who own them stay accountable for it.

  1. Register the agent as its own identity, with an owner

    The agent gets a unique identity that is not a person’s account and not a team account. The record names a human owner, a purpose, the environment it runs in and the systems it may reach.

    GuardrailNo owner, no identityEvidenceAgent registry entry

  2. Write down the tasks and the smallest scope each one needs

    List what the agent does, such as read tickets, post a comment or close a ticket. Map each task to the narrowest permission on each target. Reading and writing are separate scopes. Destructive actions are separate again.

    GuardrailScope decided at design time, per taskEvidenceTask-to-scope map, reviewed by the system owner

  3. Record the delegation when a person starts a task

    When a user asks the agent to do something, the user’s identity travels with the request. The agent never receives the user’s own credential. It receives a record that says this user asked, for this task, until this time.

    GuardrailDelegation, not impersonationEvidenceDelegation record with user, task and expiry

  4. The agent asks the broker, and the broker decides

    The agent authenticates to the broker as itself. The broker checks the agent, the user, the task and the target against policy. Actions that change or delete data, or that touch sensitive data, require a person to approve before the broker issues anything.

    GuardrailPolicy check outside the model; human approval for high-impact actionsEvidenceDecision log and approval record

  5. Issue a short-lived, narrow credential and keep it from the model

    The broker mints or releases a credential for that one task and target, with a lifetime measured in minutes where the target allows it. It is delivered to the tool layer that makes the call. The model gets the result of the call, not the secret.

    GuardrailSecret never in the prompt, the context or the tool outputEvidenceIssue record with scope and expiry; prompt and trace scans find no secrets

  6. The target authorizes the call and the log keeps both names

    The target system checks the credential itself and enforces its own permissions. The record carries the agent, the user, the task, the target, the scope and the time. It goes to a log store the agent and its owner cannot edit.

    GuardrailAuthorization in the target system, log kept outside the agent’s reachEvidenceAudit record with agent and user identity

  7. Expire, revoke and review

    The credential ends with the task or at its expiry. If the agent misbehaves, you disable the agent’s identity and everything it can obtain stops with it. The owner re-confirms the agent and its scopes on a regular rhythm, and unused scopes are removed.

    GuardrailKill switch on the agent identity; periodic owner attestationEvidenceRevocation drill result and attestation record

Example: a support agent that summarizes and closes tickets

This is an illustration, not a specific event.

Before

  • The agent runs on Priya’s personal access token, which she created last spring.
  • The token can read, edit and delete in the ticketing system and read the customer database.
  • The token sits in the agent’s config file, and the framework prints it in debug traces.
  • Closed tickets show Priya as the actor. Nobody can tell which closures were hers.
  • The token has no expiry.

After

  • The agent has its own identity and a named owner in the support team.
  • For each task it asks the broker for a token that can read tickets, or comment, or close a single ticket.
  • Closing a ticket needs a person to approve it, and the approval is attached to the record.
  • Tokens last minutes and are handed to the tool, never to the model.
  • Closed tickets show the agent as actor and Priya as the person it acted for.

How to roll it out without stalling

  1. 1. Find where agents already hold credentialsSearch repositories, pipeline variables, agent configuration and trace stores for keys and tokens. List which agent uses which credential and whose credential it is.Done whenThere is one list of agents, their credentials and the people behind them.
  2. 2. Give each agent an identity and an ownerCreate an identity per agent and stop issuing new shared keys for agent work.Done whenEvery active agent has its own identity and a named owner.
  3. 3. Put the broker in front of the first few systemsStart with the systems where a leak would hurt most, and those that already support short-lived tokens.Done whenAgents reach those systems only through the broker, and the old shared keys are revoked.
  4. 4. Carry the user’s identityAdd delegation so the record shows the agent and the person it acted for. Add human approval for high-impact actions.Done whenAn audit record answers who acted and for whom without anyone asking the team.
  5. 5. Monitor, drill and retireAlert on an agent touching a system it has never used. Rehearse revoking one agent. Remove the leftover static keys and the exceptions that have run out of reasons.Done whenA revocation drill succeeds on the clock you set, and exceptions have owners and end dates.

I keep rotation on this list for credentials that have to be long-lived, such as a static key at a legacy target. The OWASP Secrets Management Cheat Sheet says to rotate regularly so that stolen credentials work only for a short time. For agents the better lever is to avoid the long-lived credential in the first place, because a credential that expires in minutes needs no rotation schedule.

  • People stay accountable. I treat an agent as a capable assistant that works under a named owner. It does not take over the owner’s responsibility. Security, governance, monitoring and collaboration between people and the agent make it safe to rely on.
  • Measure a few things. Share of agents with their own identity, agents without an owner, longest credential lifetime, share of high-impact actions with an approval, and time to revoke one agent.
  • Exceptions have owners and end dates. A legacy target that only takes a static key goes on a register, gets reviewed, and leaves when its reason ends.

What tends to go wrong

  • The broker becomes the new single point of failure and the new big target. It holds the means to reach many systems. It needs strong access control of its own, high availability, and a plan for when it is down. Agents that cannot reach it will be tempted to fall back to a shared key, so the plan has to cover that case.
  • Scopes are too coarse to be useful. If the target offers only read and write, a read-only task cannot get a read-only credential. I record these gaps and ask the system owner for finer scopes. Meanwhile a gateway in front of the target can enforce the narrower rule.
  • Delegation turns into impersonation. A flow that quietly passes the user’s own token to the agent looks like delegation in a diagram and behaves like impersonation in the log. I check the log, not the diagram.
  • Secrets still leak through the side doors. Debug traces, error messages, tool output and environment variables are where I find them. Redaction rules catch the formats someone thought of. I prefer designs where the model never receives the secret, and I test with a planted one.
  • Tool servers pass tokens along. An MCP server or gateway that forwards the token it received to an upstream API recreates the shared key. The specification forbids it, so I check for it.
  • Approval fatigue. If every action asks a person, people click through. Keep approvals for the actions that change or delete data or carry real cost, and make the approval screen show what will happen.
  • Legacy targets resist. Some only accept a static key. Put those behind the broker, keep the key in the vault, restrict who can request it, and track them as named exceptions.

What I have learned to do differently

These are habits I keep when I look at an agent design. They come from how I run credential and access programs. They are not a record of any one project.

  • I ask whose name is on the log before I ask anything else. If the answer is a person who did not do the work, or a team account, the rest of the design review can wait.
  • I look for the secret before I look at the model. I search config, pipelines and traces for keys first. The inventory usually explains the risk better than any architecture slide.
  • I plant a test secret. I put a fake key into a prompt, a config and a tool result, then see where it turns up. That finds more than a policy document does.
  • I design for the broker being down. If the only fallback is a shared key, the fallback will become the design. I agree the failure path with the owners before launch.
  • I rehearse the kill switch. I run a drill on one agent and time it. A revocation process that has never been tried is a guess.
  • I keep people in the loop where the damage is hard to undo. I am comfortable letting an agent read, summarize and draft on its own. Deleting, paying and bulk changes go to a person.
