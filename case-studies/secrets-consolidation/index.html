Secrets Sprawl & Consolidation

How to find the credentials scattered across code, pipelines and config files, deal with them safely, and move them into one governed service that applications read at runtime.

Credential Management Platform Owner & PAM Product Owner · Last reviewed 1 Oct 2026

The short version

  • Secrets pile up in repositories, pipeline variables, config files, several vaults and chat. Until someone searches, nobody knows how many there are or who can read them.
  • Anything a scan finds is treated as compromised. Rotate it first, clean the history second, and only then move it into a governed store.
  • Migrate one application at a time, fetch at runtime, and swap static secrets for short-lived or federated credentials wherever the platform allows it. Then block new secrets at the commit and the pipeline, and retire the old stores.

The problem

Secrets accumulate faster than any team can track. A developer puts a database password in a config file to get a demo working. A pipeline needs a cloud key, so someone adds it as a variable. A team stands up its own vault because the shared one was slow to get into. A token gets pasted into chat to unblock a colleague, and it stays there.

Each of those choices made sense on the day. Added together, they leave the organization with no honest answer to four simple questions. Where is this secret stored? Who owns it? When did it last change? Who has read it? In most places the true exposure only becomes visible after an incident forces a manual search, and by then the search is rushed and the findings are already someone else’s emergency.

This page covers the consolidation work: finding the secrets, handling what you find, choosing a target, moving applications over, and making sure the old habits cannot come back. The broader service around it, with its catalog and credential lifecycle, is in Credential Management Platform Strategy, so I do not repeat it here.

How the pieces fit

On the left are the places secrets end up today. A discovery step reads them, ranks what it finds and triggers rotation. The secrets then move into one governed service, which holds them encrypted, applies access policy, issues short-lived credentials where it can, and writes an audit log to a store the service’s own administrators cannot edit. Applications, pipelines and cloud workloads fetch at runtime. When an old store has no readers left, it is retired.

The service can be one product or a small number of products behind one common way to request, rotate and report. OWASP’s guidance is to standardize and centralize the secrets management solution “with care”, and to apply the same life cycle, authentication, authorization and accounting rules across every solution you keep. What matters is that one team owns the rules and every secret has one place of record.

The workflow, step by step

Nine steps, in order. Each has a guardrail that stops the step going wrong, and a piece of evidence you can show an auditor later.

  1. Scan everything you can reach

    Start with source repositories, including their history, then pipeline definitions and variables, config files, build logs, wikis and shared documents. History matters because a secret deleted last year is still readable in an old commit. GitHub’s secret scanning, for example, scans the entire Git history on all branches, and it also looks at descriptions and comments in issues, pull requests and discussions.

    GuardrailScan results are stored with restricted access, because a finding is itself a live secretEvidenceScan report with locations, never values

  2. Treat every finding as compromised: rotate, then clean

    A secret in a repository has been readable by everyone with access to it, and by every clone and fork. I do not try to work out who might have seen it. I rotate it. GitHub’s remediation guidance says the most important step is revoking the secret with its provider, and warns that removing it from the code, pushing a new commit, or recreating the repository does not stop it being exploited. History rewriting comes after revocation, and GitHub describes it as potentially destructive and disruptive, so treat it as a decision to make on purpose.

    GuardrailRotation comes before any history rewriteEvidenceRotation record per finding, with date and who did it

  3. Rank and name an owner

    The first inventory is long. Ranking it by exposure and blast radius lets the team start with a cloud key that reaches production and leave a test-environment password for later. An advisory classifier can propose that ranking, using signals such as where the secret was found, who can read that place, and what the credential can reach. A person confirms it, and every finding gets an owner before it is scheduled.

    GuardrailThe ranking is advice, and a named person signs off the orderEvidenceRanked inventory, with owner and sign-off

  4. Choose the target store

    Write the selection criteria down before comparing products: availability and recovery, audit logging, per-application access policy, support for short-lived credentials, integration with the pipelines and platforms you actually run, and how the service authenticates the workloads that call it. Prove the choice on one or two real applications before committing the estate. I describe how I run that proof in How I Run a Privileged Access Program.

    GuardrailCriteria agreed before the product comparisonEvidenceDecision record and proof-of-concept result

  5. Migrate application by application, with runtime fetch

    Move one application at a time. The application authenticates with its own identity and asks the service for the secret when it needs it. The secret is never copied back into code, config or a pipeline variable. Keep the old copy readable but flagged until the new path is proven in production, then remove it.

    GuardrailRead access granted to the application identity only, and a change record for each cutoverEvidenceChange record and the first read in the service log

  6. Replace static secrets where the platform allows it

    A secret that expires on its own is worth more than one you rotate carefully. Where the target supports it, ask the service to generate a database login on demand with a lease. In Vault’s model, every dynamic secret has a lease with a time to live, and when the lease expires or is revoked the secret is invalid immediately. For pipelines that deploy to a cloud account, use workload identity: GitHub Actions can authenticate with cloud providers over OpenID Connect, so the job gets an access token that is available only to that run, with no long-lived cloud credential stored as a GitHub secret.

    GuardrailFederation trust restricted to named repositories and environments, with a lifetime on every tokenEvidenceTrust policy as configured, and token issuance logs

  7. Stop re-exposure at the commit and the pipeline

    Clean-up is wasted if new secrets keep arriving. Add a pre-commit hook so developers see the problem before it leaves their machine, and push protection or a pipeline scan so a secret that gets past the hook is blocked on the server. GitHub’s push protection blocks secrets in pushes from the command line, commits in the web interface, file uploads and API requests. By default anyone with write access can bypass it by giving a reason, so decide who may bypass, and make every bypass visible.

    GuardrailBlock on detection, with a logged and reviewed bypassEvidenceA planted test secret blocked in the pipeline, and the bypass report

  8. Make the service survive its own failure

    Once everything fetches from one place, that place is a dependency for every deployment. Design high availability and disaster recovery from the start. OWASP says to back up automatically, and to test restore procedures regularly so you know the backups are intact. It also recommends emergency break-glass credentials that are backed up securely in a secondary secrets management system. Test the failure on purpose, with the same people who would be on call.

    GuardrailRestore and break-glass tested on a scheduleEvidenceDrill record with timings and findings

  9. Retire the old stores

    The migration is finished only when the old paths are closed. Make the old store read-only, watch for reads, fix whatever still depends on it, then remove it. Close the ability to create new secrets there so the sprawl cannot restart. Keep the retirement record, because it answers the auditor’s question about secrets outside the platform.

    GuardrailRead-only period, then removal, with creation disabledEvidenceZero reads on the old store, and the decommission record

Example: a deployment pipeline and a database password

This is an illustration, not a specific event.

A scan finds two things in one application’s repository. A cloud access key sits in a CI/CD variable, and a database password sits in a config file that has been in the repository since its first commit.

Before

  • The cloud key is a long-lived variable that every pipeline maintainer can read.
  • The database password is in the current file and in old commits.
  • Nobody can say when either last changed, or who owns them.
  • A second team has pasted the same password into a wiki page.

After

  • Both secrets were rotated as soon as they were found, before anyone touched the history.
  • The pipeline gets a short-lived token through federation and stores no cloud key.
  • The application fetches its database login from the service when it starts.
  • An owner is named, reads are logged, and the old copies are gone.

The order is the point. Rotation happened first because the old values were already exposed. The pipeline moved to a federated identity because that removes the stored key entirely, and the database login moved to runtime fetch because the application could not use federation. The scan and the commit block then stayed on, so the same mistake would be caught the next time someone made it.

How to phase it

  1. 1. Agree the rules and find the secretsWrite down what counts as a secret, who owns the program, and what happens to a finding. Then scan, read-only, and keep the results locked down.Done whenThere is one inventory, with locations and no values, even if it is uncomfortable to read.
  2. 2. Rotate and rankRotate what the scan found. Rank the remainder by exposure and blast radius, and give each item an owner.Done whenEvery finding is rotated or has a dated plan, and the owners have signed off the order.
  3. 3. Stand up the target and prove itChoose the store against written criteria, set up access policy, logging, availability and recovery, then onboard one or two real applications.Done whenThose applications run on runtime fetch and the service has passed a restore test.
  4. 4. Migrate in waves and block re-exposureMove applications by rank, replacing static secrets with short-lived or federated credentials where possible. Turn on pre-commit and push protection or pipeline scanning early, not at the end.Done whenNew hard-coded secrets are blocked, and each wave has an accepted result.
  5. 5. Retire and keep watchingTake the old stores read-only, then remove them. Keep scanning on a schedule and review the exception register.Done whenNew secrets can no longer be created outside the service, and the exceptions have owners and end dates.

Governance: who owns what

RoleOwns
Platform product ownerThe program, the standards, the migration order and what counts as done
Platform engineeringRunning the service: availability, recovery, upgrades and integrations
Application ownersCutting each application over, and each secret’s purpose and retirement
Security architectureRotation rules, scanner settings, bypass rules and exception criteria
Internal auditIndependent checking, separate from those who run the controls
  • A finding is never a blame list. Agree before the first scan that the result describes the system and says nothing about the people who built it. Otherwise teams will hide what they have.
  • Exceptions have owners and end dates. A legacy system that cannot fetch at runtime goes on a register with a plan, a review rhythm and an expiry.
  • Measure coverage and age. Useful measures are the share of known secrets now in the service, secrets with no owner, the age of the oldest static secret, the share with an expiry, and scanner bypasses per month.

What tends to go wrong

  • The history gets cleaned and the secret does not get rotated. It looks like progress and changes nothing for an attacker who already has a copy.
  • The scan result becomes the leak. A spreadsheet of findings with the values pasted in is a new store of live secrets. Keep locations only.
  • Rotation breaks something nobody knew about. A secret copied into three places stops working in two of them. Find the consumers first and agree a window, but do not hold back the rotation of an exposed secret.
  • One service becomes one big dependency. It holds the keys to many systems, so it needs high availability, tight access of its own and a recovery plan that has actually been run.
  • The front door is too slow. If onboarding takes weeks, secrets reappear in pipelines and chat. The new path has to be quicker than the old habit.
  • The scanner gets switched off. A tool that blocks developers with false alarms will be bypassed. Tune it, and read the bypass reasons instead of banning bypass.
  • Federation trust is set too wide. GitHub’s documentation says you must define at least one condition on the trust, so untrusted repositories cannot request tokens. A wildcard condition undoes that.
  • Old stores linger. Without a retirement date, the old vault becomes a second source of truth that nobody audits.

What I have learned to do differently

These are habits I keep from running programs like this, and none of them describes one particular project.

  • I rotate before I discuss. I used to want a full picture of who had seen a secret before acting. Now I rotate first and work out the history afterwards, because the discussion can take days and the exposure continues the whole time.
  • I keep findings as locations only. The inventory records where a secret is, what it opens and who owns it. The value stays out of every report, ticket and chat message.
  • I look for the secret that does not need to exist. Before vaulting a long-lived key, I ask whether the workload can use a role, a federated token or a generated login. Each yes removes a secret to manage.
  • I turn on prevention early. I put the commit and pipeline checks in at the start of the migration, so the sprawl stops growing while I am still clearing it.
  • I take the first application seriously. The first migration sets the pattern for the rest. I pick an application with a willing owner, finish it properly and write down what we learned.
  • I test the failure path with the people who will use it. A recovery plan that only the author has read is a guess. I run the drill with the on-call team.
  • I set a retirement date when I start. Every old store gets an end date on day one, and I check the read counts before I close it.
