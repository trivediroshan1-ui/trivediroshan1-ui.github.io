Credential Tiering & the PAM Market: Closing the Tier 0 Gap

A tier is a claim about which credentials can mint access to which other credentials. This page shows how I place each credential by blast radius and use, what controls each tier gets, and where the PAM tool market fits.

Independent research · Last reviewed 1 Oct 2026

Try the 3-minute self-check →

The short version

  • A tier describes blast radius. A credential belongs in the highest tier of anything it can change or mint access to, wherever it happens to be stored.
  • Each tier gets a fixed set of controls: storage, rotation, access path, monitoring, approval and session recording. They get stronger towards Tier 0, and a credential that is valid in one tier is never valid in another.
  • PAM products are sold as capabilities such as vaulting, session management and just-in-time access, not as tiers. Work out what each tier needs first, then see which tools supply it.

The problem

Most organizations have a vault. Far fewer can say which of their credentials are worth the most to an attacker, and which controls those credentials get. So the same standard ends up applied to a helpdesk password and to the account that administers the identity provider. Either the strong controls are too expensive to use everywhere, or the weak ones sit in front of things that matter.

The usual attack path is short. Someone phishes a laptop, finds a credential that also works somewhere more valuable, and keeps moving. Nothing in that story needs a clever exploit. It needs one credential that is valid in more places than it should be. Tiering is the habit of asking, for every credential, how far it could go if it were stolen, and then drawing a hard line at each step so that it cannot go further.

Friction has a cost too. If every credential needs two approvers and a hardware key, people route around the process. If none do, the account that can rewrite your identity system is protected like a shared mailbox. Tiers are how you spend the friction where it buys the most.

Where the tier idea comes from

The Tier 0, 1, 2 language comes from Microsoft's Active Directory tier model, which was designed to contain unauthorized escalation of privilege in an on-premises Windows Server Active Directory environment. Microsoft's current guidance, the enterprise access model, builds on that model and widens it to cover on-premises, multiple clouds, internal and external users, and more. It did not throw the idea away. It renamed and split the tiers so they still make sense outside a single directory.

In Microsoft's mapping, Tier 0 becomes the control plane: identity systems, centralized access enforcement and, where it is the only option, network controls. Tier 1 is split into a management plane for enterprise-wide IT management and a data and workload plane for per-workload management. Tier 2 becomes access pathways for users and for applications and APIs. Microsoft's wording differs a little between pages, so I read the mapping as a direction. One sentence from the architecture page is the reason Tier 0 gets the most attention: compromise of the control plane often enables indirect control of all other planes.

Microsoft's privileged access strategy also defines three security levels: enterprise, specialized and privileged. At the privileged level, a person does not do sensitive work and everyday productivity tasks on the same account or device. I use that as the access-path rule for Tier 0.

Two things here are my own. I use four tiers, with Tier 3 as a home for low-impact credentials. And I place individual credentials into tiers, where Microsoft's pages talk about planes and access pathways. The credential-level placement and the control set are my working method.

How the tiers fit together

Read the diagram one row at a time. A request starts at the left, passes the controls on its tier's path, and only then reaches what it can change on the right. Tier 0 has four gates, Tier 1 three, Tier 2 two and Tier 3 one. Every row writes to the same audit log, kept outside the platform being audited.

Tier 0 holds the identity control plane: domain controllers, certificate authorities, the PAM vaults, and the admin plane of whatever runs your single sign-on. A cloud identity provider's global admin role is Tier 0 even with no server rack behind it. Tier 1 is the application, cloud and CI/CD estate. Tier 2 is workstation and helpdesk administration, the most common way in. Tier 3 is everyone else, the largest attack surface by count.

Six kinds of credential, and where each tends to land

A human admin password, a database login and an AI agent's token all open doors, but they are issued, stored and retired in different ways. I sort credentials into six classes by use, then place each one in a tier by what it can reach.

Service accountA non-interactive account that software uses to run on a host or in a directoryTier of the systems it can reachIts rights, and whether it allows interactive login. Directory rights mean Tier 0.

Machine and NHI credentials are the class I find least inventoried. An MCP server is a new case of the old service account problem: it usually holds a standing credential to whatever it connects to, and any agent that can reach it can use it. I treat it like a service account, with an owner, a tier, a scope and an expiry. The non-human identity at scale and agentic AI identity governance studies go further on this.

The control set for each tier

Every tier answers the same six questions: where the secret is stored, how it changes, what path leads to it, what watches its use, who approves a grant, and whether the session is recorded. The answers get stricter as the tier number falls. I kept the cells qualitative because intervals depend on your risk appetite and tooling.

Two rules sit above the table. A credential is valid in one tier only: if the same secret opens a Tier 2 workstation and a Tier 0 server, the table is decoration. And a time limit is one control inside a wider model. It stops access living forever, but a hijacked session can still be misused inside the window. Continuous checks such as device posture and behavior signals are worth their engineering cost at Tier 0 and on the break-glass path. A plain time limit is usually enough lower down. The just-in-time elevation study has more.

The workflow: classify, place, control, review

This is the loop I run for every credential, whether it already exists or someone is asking for a new one.

  1. Name an owner and find the credential

    Every credential needs a named person or team first. For existing credentials this is a discovery job across vaults, pipelines, directories, cloud accounts and code. For new ones it is an intake request saying what it is for and who answers for it.

    GuardrailNo owner, no credentialEvidenceInventory entry with owner and purpose

  2. Classify it

    Pick the class from the six above, then write down what it can do. Can it create or change other credentials? Edit a pipeline or a role? Log in interactively? What it can change decides the class. Where it is stored does not count.

    GuardrailClassification is based on permissions held, checked by someone other than the ownerEvidenceClassification record with the answers to those questions

  3. Place it in a tier

    Apply the mint test: what is the highest tier this credential could reach, directly or by creating something else? That is its tier.

    GuardrailThe owner cannot lower a tier alone. Tier 0 and Tier 1 placement needs security architecture sign-offEvidenceTier assignment with approver and date

  4. Apply the tier's controls and close the old path

    Configure all six controls before the credential is issued or moved. Then close the old way in: a direct login, a copy in a config file or a shared account.

    GuardrailNo issue until all six controls are set, and a test shows the old path is closedEvidencePolicy as configured, plus the result of a deliberate attempt to use the old path

  5. Review, and move it when things change

    Review on a rhythm, using usage evidence instead of memory. Also review when something changes: new permissions, a new owner, a migration finishing. Move the credential if the answer to the mint test has changed.

    GuardrailReview decisions are driven by usage, and a permission change triggers a tier checkEvidenceAttestation record and usage report

Example: a pipeline deploy key

This is an illustration, not a specific event.

A pipeline holds a cloud key to deploy an application. First placement looks easy: a cloud key used by CI/CD, so Tier 1. Then the mint test. The role behind the key can create roles and attach policies in the cloud account, so the key can give itself anything, including admin rights over the account's identity layer. Its real tier is Tier 0 until the permissions change.

Before

  • The key is long-lived and sits in a pipeline variable that every maintainer can read.
  • The role was made broad so deployments would stop failing.
  • Nobody can say which tier it belongs to.
  • It is never reviewed because the pipeline works.

After

  • The pipeline gets short-lived credentials through a workload identity and no stored key remains.
  • The role is cut down to deploy actions. Role creation is removed, so the credential drops to Tier 1.
  • The owner, tier and expiry sit in the inventory.
  • A change to the role triggers a tier check.

Where the PAM market fits the tiers

Tiers describe credentials. PAM products are packaged as capabilities, and the two do not line up one to one. Gartner defines PAM as a set of tools to control access and secure accounts that provide an elevated level of technical access, for human and machine accounts. Its capability list includes vaulting and rotation, session management, just-in-time privilege and provisioning, secrets management, command control, account discovery and onboarding, and privilege elevation. Those are the building blocks, and each tier needs a different mix.

Organization shape changes the shortlist

The shape of the organization changes which categories to look at first. This is a profile view, not a league table.

  • Large regulated enterprise. Audit depth matters most. Enterprise PAM suites such as CyberArk and BeyondTrust are the usual starting point.
  • Mid-market. Standard compliance needs without heavy overhead. Mid-tier PAM such as Delinea Secret Server is the usual fit.
  • Cloud-native and DevOps-first. Removing standing credentials and fast onboarding matter most. Cloud-native access platforms such as StrongDM and Teleport, plus cloud entitlement tooling such as Wiz, sit here. Compliance reporting is described as less mature, so pair them with identity governance if you need audit depth.
  • Small organization, first PAM deployment. The risk is having no tiering at all. Accessible platforms such as ManageEngine PAM360 get something in place quickly.

Comparison sites describe enterprise suites as heavier on cost and deployment effort. I have not checked that against vendor pricing, so read it as direction only.

Two market signals worth knowing

GitGuardian's 2026 report counts 28.65 million new hardcoded secrets in public GitHub commits in 2025. That figure covers public repositories only. I use it to show why a scanner that blocks a merge belongs in the Tier 1 controls. The second signal is consolidation. A 2026 tracker of non-human identity deals lists eight acquisitions or agreements between May and September 2026, with buyers from identity, network security, data security and credential management. It reads this as NHI turning from a standalone purchase into a capability inside larger platforms. That tracker is a secondary source built from press releases and trade reporting, so treat the count as indicative. Check whether a platform you already own offers the NHI inventory before buying another tool.

How to build it in phases

  1. 1. Agree the definitionsWrite the tier definitions and six classes on one page. Name who owns the standard and signs off placement.Done whenEvery class has a default tier, and the people who will be bound by the standard have approved it.
  2. 2. Inventory and classify, Tier 0 firstFind the credentials, give each an owner, classify them, from the control plane down.Done whenEvery Tier 0 credential is known, owned and classified.
  3. 3. Close Tier 0Put the gate in front of it, add hardware-key sign-in, two approvers and recording, and test the break-glass path.Done whenNo route into the control plane remains except the documented ones, and a boundary test proves it.
  4. 4. Tier 1 and Tier 2Move to short-lived credentials, block secrets in the pipeline, make local admin unique, replace standing admin with elevation.Done whenNew credentials in these tiers cannot be created outside the platform.
  5. 5. Tier 3, measure, retire the old pathsBring the low-risk estate in, report on the measures below, and remove the old stores and habits.Done whenThe review rhythm runs without a project team pushing it.

Governance: who owns what

RoleOwns

Security architectureTier definitions, sign-off on Tier 0 and Tier 1 placement, and boundary tests
Credential ownersThe classification of their credentials, the access list, the review attestation and the retirement

Security operationsWatching and responding to alerts on each tier
Internal auditIndependent checking, separate from the people who run the controls
  • One person never moves a credential down a tier alone. The owner proposes, someone else approves, and the record shows both.
  • Review the standard too. If every team asks for an exception to the same control, the control is wrong or the front door is too slow.
  • Exceptions have owners and end dates. Anything that cannot meet its tier's controls, such as a legacy application needing a static password, goes on a register with a plan and a date.
  • Measure coverage and drift. Useful measures are the share of known credentials classified, credentials with no owner, credentials above their tier, Tier 0 systems still reachable by a direct path, and the age of the oldest unrotated secret.

What tends to go wrong

  • Tier 0 is drawn too small. Teams list the domain controllers and forget the cloud identity provider's admin roles, the pipelines that deploy to the identity layer, or the vault.
  • The vault stops at Tier 0. Many estates have a vault at the top and little below it, yet Tier 1 and Tier 2 are where a first foothold usually lands.
  • Classification is done once. A Tier 1 credential can pick up permissions and become Tier 0 unnoticed. Review on change, not only on a calendar.
  • The gate is a single point of failure. If the vault or approval system is down during an incident, the response cannot be to wait for it. That is what a tested break-glass path is for. See break-glass access.
  • Tiers turn into org charts. Tier 0 is for credentials that can mint other credentials, not a list of senior people.
  • A product gets mistaken for a tier. A tool bought for one tier gets assumed to cover the rest.
  • Temporary credentials stay forever. Accounts made to bridge a migration get forgotten because they were never meant to last.
  • AI agents get standing access. An agent that reviews access or manages secrets needs its own tier, scope and expiry. See AI agent credential sharing.

What I have learned to do differently

These are habits from how I run this kind of work. They are not a report on any one project.

  • I ask what a credential can mint before I ask where it lives. Location is easy to see and misleading. Reach decides the tier.
  • I finish Tier 0 before I start the rest. A half-built gate in every tier gives false comfort. A complete gate on the control plane is a smaller area I can defend properly.
  • I keep the number of tiers small. When a team asks for a fifth tier, I look for a missing control in one of the four.
  • I test the boundary by trying to cross it. Reading a policy proves little. Taking a low-tier credential and attempting to use it in a higher tier shows what is real.
  • I write the tier definitions on one page and get them approved by the people they bind. If only security has read them, they last until the first incident review.
  • I judge tools after I have written what each tier needs. Then I try two or three candidates on a small slice. That settles more than a comparison table.
  • I give every temporary credential an expiry the day it is created. Cleanup backlogs do not get done.
  • I test break-glass before go-live. It is part of the Tier 0 design, so it gets built and tried before the gate goes live.
