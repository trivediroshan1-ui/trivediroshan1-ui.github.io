Hand-run in the browser lab

The script run above never opens a browser. So I also clicked through the lab at roshantrivedi.co.in/mcp-human-approval-gateway myself, on my laptop, on 10 October 2026. This lab is a separate copy of the logic that runs in the page. It does not speak MCP.

  • The reply is lost, then I retry. A human approved a production deploy and the tool did the work, but the answer never came back. Retrying with the same key returned the stored state and ran nothing again. A new key and a replay were both refused with “This authorization has already been consumed.” After the six-minute wait the state became unknown. A named person recorded the outcome as executed, and the same three retries behaved the same way afterwards. 14 events, chain verified.
  • The tool fails cleanly. Same approval, but the tool reported a failure. The failure was recorded and nothing was retried on its own. Same key returned “failed”, a new key and a replay were refused. After a clean failure the approval is still spent, so the only way forward is a new request and a new human approval. 10 events, chain verified.
  • A wrong record is accepted. I set the tool to never run, let the answer get lost, and then recorded the outcome as executed. The lab took my word and wrote it into the log, with my name and the time. It cannot check, and the log faithfully holds the wrong answer. Settling an unknown outcome is only as good as the person doing it.
  • Edit one stored event. The tamper test changes one event without redoing the hashes. Verification broke at exactly that event (event 3).
  • A private repository read. Needed a human, as expected.

Limits: the lab’s log is unsigned, and a plain hash chain only catches a careless edit. Whoever can rewrite every hash can rebuild it. The lab updates its state the instant the clock moves, while the MCP status tool can lag, so the two do not behave identically. The reason a person types when settling is not checked.

How to read this

The gateway and every tool it guards are synthetic. Nothing real is touched. Each case was run once by a script that talks to the same /mcp endpoint the MCP Inspector uses. The lost-response and clock cases run inside the test harness, because the fault switch and the clock only exist there. A separate real 11-minute wait also ended in “expired”. Reviewer names are typed into the request, not authenticated, and one case shows why that matters. This shows what this gateway did on these cases. It does not prove it secure.
