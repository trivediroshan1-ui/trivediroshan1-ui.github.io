N-R18-01: a copied key from another network

Scenario. An internal payments API accepts a static key from the billing service. In one hour there are 12 calls: 6 genuine ones from the billing workload, 3 replays of a copied key from an unknown network, and 3 calls with the old key after it was rotated 2 days ago.

Controls. The key is bound to the workload, so a call must also carry the workload's own certificate. The old key is revoked at rotation. An alert fires when a key is used from a new network.

Where my guess was wrongI guessed 3 alerts. The model gave 1, because it raises one alert per new network and all 3 replays came from the same unknown network. I had written in the guess file that a repeat from one network might be counted once, so I saw the risk and still put down the wrong number. Replays from 3 different networks give 3 alerts. The rule "one alert per new network" is a choice I made in the model, so this shows how I built it, not how a real product counts.

What it means. A key with no binding cannot be told apart from a copy of itself. With the binding, the copies are refused and the log shows which calls were bad. Revoking the old key at rotation did nothing here, because the binding already refused it. That control matters when there is no binding.

Limit. A replay made from inside the real billing workload carries the certificate and is accepted. The binding cannot see a compromised host.

N-R18-02: a test credential that opens production

Scenario. The test pipeline and the production service share one service account and one vault path. Over a day there are 8 pipeline runs in the test environment. 2 of them come from a compromised test runner that tries the production database.

Controls. A separate identity per environment. The production secret path is closed to every test identity. An alert when a test identity asks for a production secret.

The wildcardThis was the guess I thought most likely to be wrong in either direction. It was right. A production secret stored under a path like /kaveri/*/db can be matched by a test identity, and the path restriction misses it. The separate identity stopped the other attempt. Path rules written with wildcards need to be read for what they let through.

What it means. The separate identity did the real work. The path restriction only showed its value in the wildcard case, which the main scenario did not include.

Limit. Loading a real copy of production data into the test database for a refresh is not seen by any of the three controls. That is an assertion about my model, not something I measured. The model does not inspect data.

What this cannot tell you

  • I wrote the guesses and the code. A match shows my model agrees with my reasoning, not that a real product behaves this way.
  • Both are small in-memory models with made-up data.
  • Two cases cannot show how common these failures are. They show what each control does in a clear setup.
  • No product was tested, so none is endorsed or criticised.
