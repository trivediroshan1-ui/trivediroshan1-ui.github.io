The ten wrong guesses

A wrong guess is the most useful thing the lab produced. Each is recorded with what I wrote and what happened.

CaseWhat I wroteWhat happened
S-R17-05
Secrets in AI-assisted code and config		I guessed the scan would miss 1 of 8 planted secrets.It missed 2: a secret split over two lines and one in base64.
N-R14-25
Credential stolen from a CI runner, replayed		I guessed a short token lifetime would change whether a replay worked.It changed nothing. Binding the token and revoking it already refused both replays.
N-R14-07
One identity, three names		I guessed 51 entries without the control and 30 with it.The true counts are 43 and 29. Nine identities with 2 or 3 names each cannot make 51. The rule also merged two real accounts.
C-R16-C01
The forgotten service account		I guessed the secret scan on tickets would be the most useful single control.The owner rule was. It stops the chain at the first link.
N-R18-01
A copied key from another network		I guessed 3 alerts with all controls on.The result was 1 alert. The model raises one alert per new network, and all 3 replays came from the same network. Replays from 3 networks gave 3.
P-R15-06
The person never sees the password		I guessed the credential injection would matter when switched off alone, and that rotation after each session was safe to drop.The reveal policy still stopped both reveals, so the injection went unnoticed. Without rotation all 3 remembered passwords still worked.
P-R15-12
The break-glass drill		I guessed the drill would find 2 faults and that nothing finds a fault without it.It found 1. The routing check caught the alert fault before the drill ran, and the second holder made the sealed copy fault harmless without removing it.
P-R15-22
Integration with ticket system, identity provider and SIEM		I guessed 0 events arrived without controls.The connector delivers 14 of 20 and drops 6 whether or not a heartbeat exists. The heartbeat adds the alarm and the replay, not the delivery.
S-R17-08
An agent built in a low code tool and never registered		I guessed 4 agents would hold credentials at day 10 with the issue rule off, and that the 30 day expiry would go unnoticed.The scan had already flagged them and 3 owners had registered, so 1 agent holds credentials. The expiry is what disables the last one.
S-R17-09
An agent creates credentials and sub agents for itself		I guessed 4 alerts.The model alerts on each of the 5 creation attempts, refused or not. Alerting only on creations that succeed would give 1. I never wrote down which I meant.

Limits I recorded

A limit is what the control cannot see. These 33 are written down. The other 34 cases have no limit recorded, which is not the same as having none.

CaseWhat the control cannot see
N-R14-11
Application retired, identities remain		Attestation signed against an incomplete list.
N-R14-15
Rotate before consumer is updated		A consumer missing from the list still fails (report-job).
P-R15-05
Standing admin group membership		8 members remain and 2 of them are broader than they need.
P-R15-11
Break-glass used at 2 a.m.		The text is not checked for truth.
P-R15-13
Break-glass becomes a side door		A ticket number is not checked against the ticket system.
N-R14-23
Vendor breached, OAuth refresh token still valid		An allowlisted app that is breached still works until revoked.
N-R14-25
Credential stolen from a CI runner, replayed		Bound token still works from inside the runner during the job.
N-R14-07
One identity, three names		My arithmetic was wrong: 9 identities with 2 or 3 names each cannot give 51 entries; and stripping trailing digits merged two real accounts.
N-R14-22
A person logs in with a service account		A password copied during a checkout and used from another tool is not seen by the control.
P-R15-16
Help desk reset path		If the real person is also tricked into approving the notice, the account is lost with both controls on.
S-R17-10
Scheduled automations outlive the test window		An extension is accepted on any written reason.
C-R16-C06
Approval fatigue		The rule model says risk-first display only flags the request. Whether a tired approver acts on the flag is human behaviour, which this model does not test.
N-R18-01
A copied key from another network		A replay from inside the real billing workload carries the certificate, so the binding cannot see it.
N-R18-02
A test credential that opens production		A refresh job copies production rows into the test database under the production identity. None of the three controls inspects data, so this is an assertion about my model, not a measurement.
N-R14-02
Secrets in code, config, chat and tickets		A secret inside a screenshot or attachment is missed, even in a place the scans cover.
N-R14-06
An identity created outside the normal process		An administrator can create an account with a tag naming a real person who never agreed. Every check passes it.
N-R14-10
The owning team is disbanded		A team mailing list that nobody reads is accepted as an owner.
N-R14-12
Overprivileged identities		Ninety days of use cannot see a job that runs once a year, so its permission is removed too.
N-R14-13
Rotation on a schedule		A consumer that caches for 3 hours still fails during a 2 hour overlap.
N-R14-16
Retire before you rotate		The use logs miss 2 identities that sign in by an older route, so they are retired while still in use.
P-R15-01
Request privileged access with a ticket and an end time		A ticket that is open but belongs to another system is accepted. Nothing checks that it matches the task.
P-R15-04
The elevation path is down		If both nodes fail for the same reason, such as a shared database, the second node does not help.
P-R15-06
The person never sees the password		A recording tool on the user machine, or the credential in memory on the target, sits outside all three controls. This is an assertion about my model, not a measurement.
P-R15-12
The break-glass drill		An announced drill probably runs better than a real night. My model has no people in it, so it cannot show that. This is an assertion, not a measurement.
P-R15-14
Shared accounts: who did what		A person who hands their session to a colleague is still attributed, to the wrong person.
P-R15-20
Discover privileged accounts and assign owners		The last person to sign in is often not the responsible one, and a wrong owner who confirms anyway passes.
P-R15-21
Separation of duties inside privileged access		Two people approving each other's requests both pass, because each rule looks at one person at a time.
P-R15-22
Integration with ticket system, identity provider and SIEM		The heartbeat travels through the same queue it checks, so a full queue can drop the heartbeat too.
P-R15-23
Endpoint privilege management		An allowed application that can start a shell passes its elevation on to the shell.
P-R15-24
Session analytics		A large copy spread over many sessions stays under a per-session threshold.
S-R17-07
AI features inside an approved SaaS app		A file the user pastes in by hand is not covered by a limit on what the assistant fetches.
S-R17-08
An agent built in a low code tool and never registered		An agent under a personal account outside the tenant is not in the app list the scan reads.
S-R17-09
An agent creates credentials and sub agents for itself		The agent asks a person to create the key, and the person does. That sits outside all three controls.

What the numbers do not say

  • That any product passes or fails. I tested none.
  • That a control is worth its cost. I have no cost data.
  • That 57 of 67 is a good score. The guesses and models are mine, so it is a consistency check.
  • That the 34 cases with no recorded limit have no limit.
