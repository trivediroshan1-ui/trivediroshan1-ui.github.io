Machine identities, tested in public · Chapter 4

A framework for machine identities

Seven steps, drawn from what the cases showed. Targets and thresholds are yours to set.

This framework is a draft method tested only on made-up data. Every one of the 67 cases sits in exactly one step. Where a number depends on your organisation, the book says so and leaves it for you to set.

The seven steps

  1. 1. Find List every machine identity and where it lives
  2. 2. Own A named person, a purpose and an end date for each
  3. 3. Limit Least privilege and a front door that refuses the wrong caller
  4. 4. Store and issue Secrets in an approved place, short-lived, never in code
  5. 5. Rotate and expire Change on a schedule, consumers first, old value proven dead
  6. 6. Watch Use is logged and the odd use is noticed
  7. 7. Retire and respond Remove what is unused, cut access fast after a breach

Figure 4.1 The seven steps in order. What you retire drops out of the next discovery scan, so step 7 feeds step 1 again.

Flag these gaps

  • No owner.
  • No purpose.
  • No expiry.
  • Last use older than your limit (you set the limit).
  • Permissions broader than the use.
  • Secret outside the approved store.

Order the review by tier: Tier 0 and Tier 1 first. Tiers are a proposal. Tier 0 can control identity systems or all of production, Tier 1 reaches production data or systems, Tier 2 reaches little. Your organisation sets the real thresholds.

Retire in stages

Turn it off before you throw it away. If someone shouts, turn it back on. Delete only after the hold period.

  1. Monitor Watch for any use. Change nothing yet.
  2. Disable Turn it off, keep it. Rollback ready. Owner approves.
  3. Hold Wait. The owner sets the length. Re-enable if someone needs it.
  4. Delete Cannot be undone. Owner approves, backup taken.

Figure 4.2 Four stages. Only the last cannot be reversed. I have not set a hold length. That is your decision.

When a secret leaks

Do not wait for proof of misuse. Assume somebody copied it.

  1. Treat as exposed Do not wait for proof of misuse.
  2. Find the users List every app, job and person that uses it.
  3. Issue a new value Roll forward. The old one still works.
  4. Update the users Each one confirmed on the new value.
  5. Revoke the old value Only after every user is confirmed.
  6. Check the logs Look for use since the day it leaked.

Figure 4.3 Six steps. Step 5 cannot be undone, so it comes after every user has moved. Signing keys and CA keys are roll-forward only.

Never do this

Rotate the leaked key and leave the old one valid. The lab showed the same mistake in another form: 5 rotation tickets were closed while 2 old secrets still worked (N-R14-20).

Standards for new credentials

Start clean and you do not have to clean up later.

  1. An owner is named when the credential is created.
  2. An end date is set when it is created.
  3. Permissions are the least that do the job.
  4. The value is stored in the approved vault and never in code, tickets or chat.
  5. Prefer short-lived and per-job credentials to long-lived shared ones.
  6. Use is logged, and the log names who or what used it.
  7. An AI agent has its own identity and a named human owner. No shared agent identity.

In the lab, a front door that refused new identities without an owner, scope and expiry (N-R14-18) stopped the problem at creation. A weekly sweep also disabled expired keys (S-R17-04).

What is left for you to set

  • Tier thresholds, idle limits and the hold period. Your organisation sets them. They are not set here.
  • Reference points I read while building the method: the OWASP list above, and the identity and access controls in NIST SP 800-53 and ISO/IEC 27001. I name them as reading. I do not quote their text and I do not claim alignment.
  • Not yet tested: cloud-specific key habits, Kubernetes workload identity, and any real product.
