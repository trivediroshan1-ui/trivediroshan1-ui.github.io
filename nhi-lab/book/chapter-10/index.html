Machine identities, tested in public · Chapter 10 · Framework step 6 of 7

Step 6: Watch

Use is logged and the odd use is noticed.

Use of a credential is logged and the odd use is noticed. The cases here cover break-glass accounts, shared accounts, the drill, session analytics and the integration feed. Break-glass is the one place where use is expected to be rare and loud.

What the cases in this step showed

  • Break-glass used at 2 a.m. went unnoticed without an alert.
  • Used for routine work on four days, it was noticed only because a monthly report flagged 2 uses with no ticket.
  • In one chain test the alert reported the reuse and the rotation stopped it. They are not the same control.
  • The break-glass drill found 1 fault, not the 2 I guessed, because the routing check had already caught one.
  • Session analytics flagged 4 of 5 odd sessions and 10 normal ones. A 950 MB copy never reached the 1000 MB threshold.

A question to ask

If your break-glass account were used tonight, who would know by morning?

7 cases follow. Guesses that were wrong: P-R15-12, P-R15-22. Controls nothing noticed: P-R15-14, P-R15-24.

P-R15-12 The break-glass drill

Step 6: Watch · Run 4 · Privileged access · Guess wrong · Limit recorded

A quarterly drill with 4 steps: the alert fires, an on-call person acknowledges within 15 minutes, the sealed copy is found, and the password is rotated afterwards. Two faults are planted: the alert still goes to a person who left, and the sealed copy is with a person on leave.

Diagram for case P-R15-12: see it on the lab page.

GUESSWrong. I guessed the drill would find 2 faults and that nothing finds a fault without it. It found 1. The routing check caught the alert fault before the drill ran, and the second holder made the sealed copy fault harmless without removing it.
MEASUREDWithout: faults found 0, faults fixed 0, first run failures none, steps pass second run none. With: faults found 1, faults fixed 1, first run failures 0, steps pass second run 4.
EXTRA SCENARIORouting check off. Result matched my guess.
EXTRA SCENARIOSecond holder off. Result matched my guess.
EXTRA SCENARIODrill off. Result differs from my guess: {'faults_found': [0, 1]}.
TAKE-AWAYThe drill found 1 fault, not 2. The routing check caught the alert fault before any drill ran, and the second holder made the sealed copy fault harmless without removing it. An announced drill may be easier than a real night, which a model with no people in it cannot show.

P-R15-22 Integration with ticket system, identity provider and SIEM

Step 6: Watch · Run 4 · Privileged access · Guess wrong · Limit recorded

20 privileged sessions in a day. The ticket system links each session to a ticket. The identity provider syncs group changes. The SIEM receives an event per session. The SIEM connector drops events when its queue is full. One leaver is removed at the identity provider 1 hour before the sync reaches the vault.

Diagram for case P-R15-22: see it on the lab page.

GUESSWrong. I guessed 0 events arrived without controls. The connector delivers 14 of 20 and drops 6 whether or not a heartbeat exists. The heartbeat adds the alarm and the replay, not the delivery.
MEASUREDWithout: tickets linked 0, siem events arrived 14, lost unnoticed 6, heartbeat alarmed no, leaver session in gap 1, leaver access after sync yes. With: tickets linked 20, siem events arrived 20, lost unnoticed 0, heartbeat alarmed yes, leaver session in gap 1, leaver access after sync no.
EXTRA SCENARIOHeartbeat off. Result matched my guess.
EXTRA SCENARIOSync off. Result matched my guess.
EXTRA SCENARIOTicket link off. Result matched my guess.
TAKE-AWAYTickets were linked for all 20 sessions, and the heartbeat raised an alarm for lost events. The connector delivered 14 of 20 either way, so I was wrong that nothing arrived without controls. A heartbeat that goes through the same full queue it checks can miss the loss.
