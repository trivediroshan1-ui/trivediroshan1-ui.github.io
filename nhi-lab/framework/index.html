Framework

A lifecycle for machine identities and their secrets

Seven steps from finding an identity to retiring it, with the decision each step needs and the lab case that tested it. Draft v0.1, 2 November 2026. It is a working method, not a standard, and it was tested only on made-up data.

  • Last reviewed 2 November 2026
  • Built from the lab's 46 cases
  • For security and identity leads

Who this is for and how to use it

You run identity, privileged access or cloud security and you want one method for the credentials nobody talks about: service accounts, API keys, tokens, certificates, workload identities and the logins AI tools now hold.

Use it in this order. Build the inventory, find the gaps, tier what you found, decide per credential, retire in stages, and set standards so new ones start clean. Where the page says you set it, the number depends on your organisation and I have not guessed it.

LimitsThis framework came out of 46 cases on made-up data. The models are small and I wrote both the guesses and the code. Treat the lab results as examples of what to check, and test each control in your own environment before relying on it. Kubernetes and cloud workload identity design, and vault onboarding, are outside this page.

The seven steps

  1. Find: list every machine identity and where it livesBuild one list from every source: the directory, the cloud, the CI settings, the SaaS apps, the repositories and the AI tools people have connected.One list. Each row shows which source it came from.Lab evidence. A directory-only scan found 12 of 27 identities. Merging all three sources found 27. Cases: N-R14-01, P-R15-08, N-R14-07, S-R17-06.
  2. Own: a named person, a purpose and an end date for eachGive each identity a named person, a purpose and an end date. If there is no owner, escalate, then stage the identity for disable.Every row has a person who can say what it is for.Lab evidence. A key with no owner stayed active on day 31 without a rule. With the rule it was paused on day 31. Cases: N-R14-09, N-R14-18, P-R15-18, S-R17-03, S-R17-04, N-R14-21.
  3. Limit: least privilege and a front door that refuses the wrong callerTier by blast radius, give each identity the least that works, and put a front door in front of new and privileged ones.A caller with the wrong identity or too much reach is refused, and the log says who asked.Lab evidence. A low-value workload asked for a high-value role and got it. With trust bound to one workload it was refused. Cases: N-R14-17, P-R15-05, P-R15-07, P-R15-09, N-R14-22, P-R15-10, P-R15-16, S-R17-02, C-R16-C06, C-R16-C17.
  4. Store and issue: secrets in an approved place, short-lived, never in codeKeep values in the approved vault. Prefer short-lived and per-job credentials. Scan code and config before commit.No value in code, tickets or chat. A planted secret is blocked before it reaches the repository.Lab evidence. The scan blocked 6 of 8 planted secrets. The 2 it missed matched no pattern. Cases: N-R14-03, S-R17-05, N-R14-24, N-R14-25, P-R15-15, C-R16-C01, C-R16-C02.
  5. Rotate and expire: change on a schedule, consumers first, old value proven deadUpdate the consumer first, then rotate, then prove the old value is dead. Close the ticket only after that.The old value is refused. No application fails at the next connection.Lab evidence. Closing 5 rotation tickets without the check left 2 old secrets live. Cases: N-R14-04, N-R14-05, N-R14-14, N-R14-15, P-R15-02, P-R15-03, N-R14-19, N-R14-20, P-R15-25.
  6. Watch: use is logged and the odd use is noticedLog every use. Alert on the odd one: break-glass at 2 a.m., a grant used from a new place, a job that never ran before.Someone is told the same day, and the account is rotated after break-glass use.Lab evidence. Break-glass used at 2 a.m. went unnoticed. With the alert it fired and the password was rotated. Cases: P-R15-11, P-R15-13, C-R16-C05.
  7. Retire and respond: remove what is unused, cut access fast after a breachMonitor, then disable with a rollback window, then delete only after a hold period. After a vendor breach, revoke their grants.Nothing deleted that someone still needs. Access to a breached vendor ends within your target time.Lab evidence. After an app was retired, all 3 of its identities still worked 90 days later. With the rule all 3 were disabled. Cases: N-R14-11, P-R15-17, S-R17-01, N-R14-23, P-R15-19, S-R17-10, C-R16-C04.

Flag these gaps

  • No owner.
  • No purpose.
  • No expiry.
  • Last use older than your limit (you set the limit).
  • Permissions broader than the use.
  • Secret held outside the approved store.

Order the review by tier: Tier 0 and Tier 1 first. I use tiers as a proposal: Tier 0 can control identity systems or all of production, Tier 1 reaches production data or systems, Tier 2 reaches little. Your organisation sets the real thresholds.

Deciding what to do with each credential

Disabling can break something, so it needs the owner. Deleting or revoking cannot be undone, so list first, get approval and wait out a hold period.

Retire in stages

Turn it off before you throw it away. If someone shouts, turn it back on. Only delete after the hold period ends.

When a secret leaks

Do not wait for proof of misuse. Assume somebody copied it.

Never do thisRotating the leaked key and leaving the old one valid. The lab showed the same mistake in another form: 5 rotation tickets closed while 2 old secrets still worked (N-R14-20).

Standards for new credentials

Start clean and you do not have to clean up later.

  1. An owner is named when the credential is created.
  2. An end date is set when it is created.
  3. Permissions are the least that do the job.
  4. The value is stored in the approved vault, never in code, tickets or chat.
  5. Use is logged and someone is told when the pattern changes.
  6. AI agents get their own identity, a named human owner and short-lived tokens. No shared agent identity.

In the lab, a front door that refused new identities without an owner, scope and expiry (N-R14-18) stopped the problem at creation. A weekly sweep also disabled expired keys (S-R17-04).
