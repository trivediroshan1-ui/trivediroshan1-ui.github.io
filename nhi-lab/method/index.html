What we did

How the lab was run, step by step, with the mistakes

I wrote my guesses, locked them with a hash, then wrote the code and ran every case twice, once without the control and once with it. This page is the full procedure, the dates, and the places I got it wrong.

  • Last reviewed 2 November 2026
  • 46 cases in two runs
  • Made-up data only

The question

Do the controls people recommend for machine identities stop the failures they are meant to stop, and would anything tell you if one stopped working?

In scope

Finding service accounts, owners, rotation, front doors for new identities, just-in-time and recorded privileged access, break-glass, vendor access, and AI tools holding credentials. Chain tests that join several failures.

Out of scope

Any real product, any real company's data, performance, cost, and legal or regulatory compliance. The models are small and run in memory.

Why guesses first

A test you design after seeing the result will agree with you. A hashed guess file shows the guess was fixed first. It does not prove I did not cheat, but it makes cheating visible to anyone who checks.

The procedure in one picture

The procedure, as steps you could repeat

Each step says what you should see afterwards. The shasum and git steps I ran on my Mac. The Python commands I ran in the build machine, a cloud sandbox, on 2 November 2026, and the Mac run of the second run matched it.

  1. Pick the case.Take a row from the catalogue and shrink it to one failure with a control that should stop it.One sentence: what goes wrong, and which control should prevent it.
  2. Write the guess.Write what you expect with no control and with the control. Be specific: numbers, not "better".Two lines per case in a guess file. Nothing is run yet.
  3. Hash the guess file.Run shasum -a 256 guesses-file.md on the Mac. Give it the file name; without one the command waits for input.A 64-character hash.
  4. Commit the file, then note the hash.Commit the guess file on its own, before any code.A commit hash from before the code exists.
  5. Write the model.A small in-memory simulation of the control. Made-up data only (a fictional bank, Kaveri Finance).Code that runs without a network or a real system.
  6. Run with the control off, then on.Compare each result with the guess.A match, or a recorded mismatch with both numbers.
  7. Switch each control off alone.If the result does not change, no check noticed that control. Another control may be covering it, or the control may not matter for this case.A "noticed" or "NOT noticed" for each control.
  8. Write down the limit.For every case, say what the control cannot see.A limit line, or a note that none was found.
  9. Run it again on a second machine.Run the same code on the Mac and compare the output with the sandbox.Identical output. If it differs, stop and find out why.
Careful with the commitCommit only the guess file before the code. On my Mac I ran git add with no paths once, and I ran a hash command with no file name, which waits for input. Both are harmless, and both cost time.

What the words mean

Words used on these pages
TermMeaning here
MatchThe result equals what the guess said, in both runs.
Wrong guessA number or a ranking in the guess did not equal the result. The page keeps both.
NoticedSwitching that one control off changed a result.
MaskedSwitching it off changed nothing, because another control already stopped the same thing, or the control did not matter in that case.
LimitWhat the control cannot see. Every case should have one.
Chain testA series of links an attacker needs. The test records which link each control stops.

What went wrong

Mistakes, in the order they matter. The first four are wrong guesses. The last two are mistakes in my own test harness.
What went wrongCaseWhat I did
Guess wrong: the scan missed 2 secrets, not 1S-R17-05Recorded. The 2 misses matched no pattern.
Guess wrong about which control matteredN-R14-25I expected a short token lifetime to change the replay result. Another control already blocked both replays, so it did not.
Guess wrong: my own arithmeticN-R14-07Nine identities with two or three names each cannot make 51 entries; the count is 43. A rule that stripped trailing digits also merged two real accounts. Recorded.
Guess wrong: which control matters mostC-R16-C01I expected the ticket scan to matter most. The owner rule did.
Bad test data on the first runN-R14-07I had given 21 identities one shared owner, so the merge collapsed them to 11. I fixed the data and kept the first-run file as RESULTS-stretch-first-run.md.
Harness slipC-R16-C04An extra scenario ignored its "late" marker. I fixed it so the marker sets the attack day to 120, and re-ran.

What this method cannot tell you

  • I wrote the guesses and the code. A match shows my model agrees with my reasoning, not that a real product behaves that way.
  • A hash proves the file did not change after I committed it. It does not prove when I wrote it, beyond the commit time.
  • Chain tests are rule models. Each link is stopped by the controls I decided stop it, so their results follow from my rules.
  • Three chain tests had an extra scenario written after the fact to probe a limit. I marked them as extras.
